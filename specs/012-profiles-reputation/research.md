# Research: User Profiles and Reputation

## #1 Opening a profile requires the *viewed account* to currently hold membership too, not only the viewer

**Decision**: `getProfile(communityId, accountId, viewerAccountId)` calls `requireCommunityMembership()` twice — once for `viewerAccountId` (FR-006, rejects `not_a_member`) and once for `accountId`, the profile subject (rejects `not_found`). Both must hold current membership in `communityId` for the call to succeed.

**Rationale**: spec.md's own edge case originally assumed a departed member's profile "remains viewable" to current co-members, reasoning by analogy with 010-transaction-logging's "a log is retained after membership loss." That analogy breaks down for one field this feature specifically requires: the member-since date (FR-002, FR-007) is sourced from `Membership.createdAt` for the community being viewed — but this schema's `Membership` model has no soft-delete column at all (`prisma/schema.prisma`: `id, accountId, communityId, role, createdAt, operationalEpoch`, nothing else), meaning a member's removal or departure deletes their `Membership` row outright. Once that row is gone, there is no member-since date left to render, and the profile's own FR-002 whitelist has no defined fallback for "date unknown." Requiring the profile subject to also currently be a member sidesteps this by construction: if `getProfile()` can render a member-since date at all, that date is guaranteed live and accurate. The confirmed-transaction count, average rating, and review count are unaffected either way, since they are global (research.md #5) and read through `Transaction`/`Review`, neither of which depends on any `Membership` row still existing.

**Alternatives considered**: Storing a `Membership.leftAt` or making it a soft-delete row — rejected as a schema change to an existing, shipped model (003/004) with no other feature requiring it, pure speculative scope for this feature alone (Principle VII). Falling back to the account's global `createdAt` when no current `Membership` row exists — rejected because it would silently render a different *kind* of date (global account age, not "member of this community since") under the exact same "Member since" label with no way for a viewer to tell which one they're looking at, which is worse than simply not being able to reach the profile.

## #2 `Review` carries no `communityId`; the one place community matters at creation is derived transiently through the transaction

**Decision**: `Review` has five columns — `id`, `reviewerId`, `reviewedId`, `transactionId`, `rating`, `createdAt` — and no `communityId` column, no relation to `Community`. `createReview()` needs the community only once, to run the two live co-membership checks (FR-019); it reads `Transaction.communityId` for that single purpose and never persists it.

**Rationale**: Every other per-community model in this codebase (`Listing`, `MessageThread`, `Invitation`, `Membership`, and `Transaction` itself) carries `communityId` as a first-class, denormalized column specifically so every access rule can filter by it directly. `Review` is the first model in this codebase for which the feature's own spec (Clarifications) requires the *opposite*: reputation numbers are computed globally, never filtered by community, and FR-011 goes further, requiring that no response reveal *which* community any contributing rating came from. Storing `communityId` on `Review` would invite exactly the kind of per-community grouping/breakdown FR-011 forbids, for a value this feature never needs to query by. Deriving it transiently through `transactionId → Transaction.communityId` at creation time is sufficient for the one check that needs it and leaves nothing on the row to accidentally leak later.

**Alternatives considered**: Storing `communityId` on `Review` for consistency with every other model, simply not using it for filtering — rejected: an unused-but-present column is an attractive nuisance (the first future contributor to touch this code would reasonably assume it exists to be queried, reintroducing the exact leak FR-011 forbids) and provides no benefit here, since the one place community matters is already served by the join through `transactionId`.

## #3 A review's reviewed account is derived server-side from the transaction, never client-supplied

**Decision**: `createReview(communityId, transactionId, reviewerAccountId, rating)` takes no `reviewedAccountId` parameter. It loads the `Transaction`, confirms `reviewerAccountId` is either `recorderId` or `counterpartId`, and sets the reviewed account to whichever one `reviewerAccountId` is not.

**Rationale**: Exactly the same reasoning 010-transaction-logging already established for its own counterpart derivation (its research.md #2): accepting a separate `reviewedAccountId` field would require validating that it actually matches the transaction's other participant anyway, so deriving it directly collapses that validation into the lookup itself. It also makes FR-014 ("a review naming its own reviewer as the reviewed account MUST be rejected") a structural guarantee rather than a runtime branch — there is no field for a caller to even attempt setting equal to their own id.

**Alternatives considered**: None seriously — this is a direct reuse of an already-proven pattern in this exact codebase, for the exact same shape of problem (two-participant resource, derive the "other one" server-side).

## #4 Review creation tolerates a `SUSPENDED` community, mirroring `confirmTransaction()` rather than `recordTransaction()`

**Decision**: Every `requireCommunityMembership()` call inside `createReview()` — for the reviewer (FR-019) and for the reviewed account (FR-019) — passes `{ allowSuspended: true }`.

**Rationale**: A rating can only ever be left on a transaction that has already reached `CONFIRMED` (FR-012) — by definition, something already completed and underway, not new growth. This is the same category 010's own research.md #4 places `confirmTransaction()` in ("completing something already underway... mirrors `sendMessageToListingOwner()`'s exact split"), as distinct from `recordTransaction()`'s new-growth-requires-`ACTIVE` rule. Requiring `ACTIVE` for review creation would mean a community's suspension — a moderation action aimed at slowing new activity — retroactively blocks members from finishing rating deals that already happened, which is not what suspension is for (009-platform-administration's own stated purpose is blocking "new listings or membership growth" while preserving existing-thread activity).

**Alternatives considered**: Requiring `ACTIVE` for consistency with `recordTransaction()` — rejected for the same reason 010 itself rejected requiring `ACTIVE` for `confirmTransaction()`: it conflates "starting something new" with "finishing something already underway."

## #5 The three reputation numbers are computed with a single unfiltered query per number — no `communityId` in any `where` clause

**Decision**: `getReputationSummary(accountId)` runs `prisma.review.aggregate({ where: { reviewedId: accountId }, _avg: { rating: true }, _count: { rating: true } })` and `profileService.ts`'s confirmed-transaction count runs `prisma.transaction.count({ where: { confirmationState: "CONFIRMED", OR: [{ recorderId: accountId }, { counterpartId: accountId }] } })` — neither includes `communityId` anywhere. The community being viewed is used only for the profile-access gate (research.md #1) and for scoping active listings (FR-007); it never reaches either aggregate query.

**Rationale**: This is the most direct expression of Clarifications' resolution ("global, matching the confirmed-transaction count exactly") and of FR-011's non-disclosure requirement — there is no per-community intermediate result to accidentally expose, because no per-community grouping is ever computed in the first place. A `groupBy(["communityId"])`-then-sum approach would work numerically but would require deliberately *discarding* the per-community breakdown before it ever reaches a response, which is a strictly worse design: it computes the exact information FR-011 says must never be disclosed and then has to remember not to disclose it, rather than never computing it at all.

**Alternatives considered**: Computing per-community subtotals and summing them in application code (e.g., to eventually support a "your rating in this community" feature) — rejected as speculative scope with no present consumer (Principle VII); nothing in spec.md asks for a per-community reputation view, and FR-011 explicitly forbids showing one.

## #6 Making a display name clickable (FR-005) requires widening two existing service result shapes; three call sites already have what they need

**Decision**: `messageService.ts`'s `ListThreadsResult`/`ListMyThreadsResult` and `transactionService.ts`'s `GetTransactionResult`/`ListTransactionsResult`/`ListTransactionsForThreadResult` each gain one field — `counterpartId` — alongside the `counterpartDisplayName` they already return (the underlying account id is already loaded internally to compute `counterpartDisplayName`; only the return object changes). `messageService.ts`'s `getThread()` needs no change: its `messages[]` already includes `senderId` alongside `senderDisplayName`. `listingService.ts`'s `ListListingsResult`/`GetListingResult` need no change: both already include `ownerId` alongside `ownerDisplayName`.

**Rationale**: A "clickable display name" is a `Link` to `/communities/{communityId}/members/{accountId}` — it needs the target account's id at the exact place a display name is already rendered. Auditing every existing call site up front (rather than guessing) found the account id was already present in three of the five places FR-005 names (listing owner, on both `listingService.ts` result types; message sender, on `getThread()`) and absent in the other two (transaction counterpart; thread-list counterpart) purely because those two result types were only ever asked for a display name before now, not the underlying id. Widening a result object that already computes the value internally is the smallest possible change — no new query, no new join, no behavior change to the value itself.

**Alternatives considered**: Re-deriving the id on each page by re-fetching (e.g., a second lookup keyed by display name) — rejected outright: display names are not unique (006-user-display-names FR-003), so a display name cannot be reversed into an account id at all, only carried alongside it from the query that already resolved it.

## #7 The rating-creation route nests under the existing transaction resource, not a new top-level namespace

**Decision**: `POST /api/communities/{communityId}/transactions/{transactionId}/reviews` — a new sub-resource of the existing `transactions/{transactionId}` route, exactly like 010's own `transactions/{transactionId}/confirm`.

**Rationale**: A review is meaningless without the specific confirmed transaction it is about (FR-012, FR-013) — it is never created as a standalone resource with a transaction reference chosen afterward. Nesting under the transaction it belongs to mirrors 010's own `confirm` action precedent exactly, and means `communityId`/`transactionId` are already in the URL and in scope for every gate `createReview()` needs, with nothing extra to parse from a request body beyond the rating itself.

**Alternatives considered**: A top-level `POST /api/reviews` accepting `transactionId` in the body — rejected as inconsistent with this codebase's own routing convention (010, 011, 008 all nest a resource's actions under that resource's own path) for no benefit, since every real caller is already on that specific transaction's page when they choose to rate it (mirrors 010's own research.md #7 reasoning for why the "record transaction" action lives on the thread page rather than a generic top-level endpoint).

## #8 `Review` has no `operationalEpoch` column

**Decision**: Unlike `Listing`, `MessageThread`, `Invitation`, `Membership`, and `Transaction`, `Review` is not stamped with the community's `operationalEpoch` at creation, and is never filtered by it.

**Rationale**: `operationalEpoch` exists to detect whether a row predates a community's archive/restore cycle (009-platform-administration, research.md #8 there), which only matters for a row that is filtered *by community*. `Review` has no `communityId` (research.md #2) and its aggregates are already, deliberately, never filtered out by anything community-related (research.md #5) — mirroring `Transaction`'s own already-established precedent that a confirmed log is "never filtered out... based on a stale `operationalEpoch`" (010, research.md #6), since Constitution Principle IV treats it as a permanent source of truth. A `Review` tied to a `Transaction` that itself is never hidden by an epoch change would have nothing meaningful to compare its own epoch against.

**Alternatives considered**: Stamping it anyway for mechanical consistency with every other per-community-adjacent model — rejected as a column with no reader and no purpose, given `Review` has neither a community to compare against nor any code path that would ever filter by it.
