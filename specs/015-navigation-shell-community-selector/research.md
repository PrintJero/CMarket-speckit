# Phase 0 Research: Navigation Shell and Community Selector

## 1. Does an "active community" tracking mechanism already exist?

**Investigation**: Repo-wide search for `activeCommunity|currentCommunity|lastCommunity|active_community|selectedCommunity` returned exactly one hit, in `specs/008-listing-messaging/plan.md`, describing `getCurrentAccount()` building a cross-community sidebar payload via `communityId: { in: currentCommunityIds }` — that is enumerating *all* of a member's current memberships for sidebar display, not tracking which *one* is currently active. Direct reads of `src/lib/auth/currentAccount.ts` (the canonical `getCurrentAccount()`), the `Session` Prisma model, and `sessionService.ts` confirm: `Session` currently has only `id`, `accountId`, `sessionToken`, `createdAt`, `expiresAt`; `getCurrentAccount()` returns the full membership list with no concept of "current selection"; `app/page.tsx` today has no selection step at all — a member with memberships just sees a static "Pick a community from the sidebar" message.

**Decision**: No such mechanism exists. This plan introduces the first one, in the smallest form that satisfies the spec's own Assumptions ("how that association is stored ... alongside the existing session record ... is a planning-level concern"): a nullable `activeCommunityId` column directly on the existing `Session` row.

**Rationale**: The mandate to "reuse the existing mechanism, don't fork a second one" presupposes something to reuse; since nothing exists, the closest-fit interpretation that is still faithful to its intent is: don't introduce a *second*, competing way of tracking active community later in this same feature (e.g., a client-only `localStorage` value used by some screens while the server session field is used by others). Everything in this plan — the entry-point router, the selector, the main view, the sidebar switcher — reads and writes the one `Session.activeCommunityId` column through one small set of functions in `sessionService.ts`. Piggybacking on `Session` (rather than a new table, a cookie, or `Account`) is also the most literal reading of the spec's own Assumptions section, and matches its stated lifecycle exactly: a fresh sign-in creates a fresh `Session` row with `activeCommunityId = null`, so "a new session always starts with no remembered active community" falls out for free with no extra logic.

**Alternatives considered**:
- *New dedicated table (e.g. `ActiveCommunitySelection`)* — rejected: adds a second store for what is conceptually one scalar per session; violates Principle VII for no benefit, since the value has no lifecycle independent of the session it belongs to (deleting the session should trivially "forget" the active community, which a same-row column gives for free via cascade).
- *Cookie-only (client-set, unvalidated) value* — rejected outright: FR-001b requires live re-verification against current membership on every read, which means the value must be checked server-side regardless; a client-trusted cookie would need that same server check anyway, so storing it server-side alongside the session is strictly simpler and removes an entire class of forged/stale-cookie handling.
- *Field on `Account`* — rejected: the spec is explicit that this is session-scoped, not account-scoped ("a new session always starts with no remembered active community"); a member signed in on two devices must be free to have two different active communities, which an `Account`-level field would prevent.

## 2. Naming the exact 012-profiles-reputation read path (trust-visible cards)

**Decision**: The main view's listing/wanted cards call a new `getReputationSummaries(accountIds: string[])` in `src/server/services/reviewService.ts` — a batched sibling of the already-exported `getReputationSummary(accountId)` (used today by `profileService.ts`'s `getSelfProfile()`/`getProfile()`). Both are built on the identical underlying `prisma.review.aggregate` shape (`{averageRating, reviewCount}`), grouped by `revieweeId` for the batched form instead of filtered to one id. This is a real, unmocked integration with 012's own data — not a new parallel reputation computation.

**Rationale**: A feed page can show many listings from many distinct owners; calling the existing single-account `getReputationSummary()` once per card would be an N+1 query pattern this plan explicitly avoids (Technical Context: Performance Goals). Adding one batched query function in the same file, next to the one it mirrors, is the smallest change that avoids N+1 while keeping the read path exactly where 012 already put it — no new file, no new service.

**Verification badge ("verified community member")**: this is the existing current-membership-in-this-community fact, computed the same way it already is in three other places in the codebase (`getCurrentAccount()`, `listMyListings()`, `listMyThreads()`, and `profileService.ts`'s `getCurrentMembershipsWithDetails()`): a `Membership` row whose `operationalEpoch` matches its `Community`'s current `operationalEpoch`. `profileService.ts` documents this explicitly as an intentionally *not* cross-module-extracted convention ("kept local to this file ... matching that same established per-service-duplication convention, Constitution Principle VII"). This plan follows that same precedent: the main view computes current-membership for the page's distinct owner ids with one batched `prisma.membership.findMany` scoped to the active `communityId`, rather than importing a helper from `profileService.ts` (014-account-public-profiles is not one of this feature's declared reuse targets, so it is not touched).

**Alternatives considered**:
- *Call `getReputationSummary()` once per card* — rejected: N+1 queries per feed page.
- *Extract a shared `getCurrentMembership` helper into a new cross-module util* — rejected: contradicts the codebase's own stated, deliberate convention of per-file duplication for this exact predicate (Principle VII, as documented in `profileService.ts` itself).

## 3. Re-verifying the remembered active community as a live membership (FR-001b)

**Decision**: `getCurrentAccount()` — the single existing function every screen already calls for session/account context — is extended to read `Session.activeCommunityId` and, before including it in its returned payload, check it against the same `requireCommunityMembership()` gate already used by `listListings()`/`createListing()`/etc. in `listingService.ts`. If the stored id is null, or the check fails (no longer a member, or the community is `ARCHIVED`), `getCurrentAccount()` returns `activeCommunityId: null` for that call — it is never trusted as a cached value.

**Rationale**: This makes "live re-verification" true by construction rather than by convention: there is exactly one function that produces "what is the active community," and it is incapable of returning a stale one, because it re-derives the answer from the database on every call using the same membership gate every other community-scoped action already uses. No separate cache, no separate invalidation logic to keep in sync.

**Alternatives considered**:
- *Trust the stored value and only re-check on the entry-point route* — rejected: FR-001b says "every return visit," and other entry points exist (sidebar switcher, deep links); re-checking inside `getCurrentAccount()` itself covers all of them for free instead of requiring every call site to remember to re-check.

## 4. Where the main view's feed logic lives (Story 2, FR-006–FR-008)

**Decision**: `app/communities/[communityId]/page.tsx` (new) calls `listListings(communityId, accountId, { kind, search })` — the exact function and community-scoping gate the existing `app/communities/[communityId]/listings/page.tsx` already uses. The new page presents a simpler control set matching the spec (a search box and a two-way "For sale/Wanted" segmented control) and omits the price-range filter that page also exposes, since price filtering was never requested for this feature (Principle VII: don't port unrequested scope). The existing `/listings` page is left exactly as-is — it remains reachable (e.g. from "My listings" management flows) and is not superseded structurally, only no longer the thing a member sees immediately upon choosing a community.

**Rationale**: This satisfies FR-022/the reuse mandate literally: the "For sale"/"Wanted" toggle and the search behavior are 100% the pre-existing `listListings()` behavior; only the surrounding page and its control markup are new.

**Alternatives considered**:
- *Redirect `/communities/{id}` straight to the existing `/communities/{id}/listings` page* — considered and rejected only because that page's control set (price range fields, a `<select>` for kind) does not match the spec's explicit "one clean segmented control" main-view requirement (Story 2) or the design direction's card requirements (trust signals); reusing its *query function* while giving it a purpose-built presentation layer satisfies both the reuse mandate and the spec's UI requirements.

## 4a. Where the deep-link "set this as active" write happens

**Decision**: `app/communities/[communityId]/page.tsx`'s server render never writes anything. It passes the account's currently-known `activeCommunityId` as a prop to the client component `MainViewControls.tsx`, which — in a `useEffect` that only runs after hydration — calls `POST /api/active-community` (the same route the selector and sidebar switcher already use) when the two ids differ, then calls `router.refresh()` once that resolves. The refresh exists because `AppShell`'s sidebar reads `activeCommunityId` from the same server-rendered `account` prop this page received; without it, a member arriving via a raw deep link would see the sidebar still reflecting no (or the previous) active community until their next unrelated navigation, even though the write already succeeded.

**Rationale**: An earlier draft of this plan had the page's server render itself call `setActiveCommunity()` directly whenever the visited `communityId` differed from the session's stored one, to cover genuine deep links without a separate round trip. That is unsafe: Next.js's `<Link>` prefetching fetches a route's RSC payload — running its server component function — whenever a link scrolls into view or is hovered, with no user navigation intent and no client JavaScript execution; the same is true of a crawler or uptime monitor hitting the route with a forwarded session cookie. A write inside the render body would let any of those silently reassign a member's active community. A post-hydration client effect cannot fire from prefetching or a bodiless crawler request — it only runs once a real navigation has completed and the page has mounted in a browser — so it covers the same deep-link case without that risk. It also collapses to one single write path: every way of becoming active (selector, switcher, deep link) now goes through the one `POST /api/active-community` route, rather than that route being one of two places that can write the value.

**Alternatives considered**:
- *Write during server render (the original draft)* — rejected for the reason above.
- *A Server Action invoked directly from the page* — rejected as unnecessary: it would still need to be triggered by a client-side event (mount) to avoid the same prefetch problem, at which point it's simpler to call the one already-existing, already-validated API route than to introduce a second write mechanism (Server Action) alongside it.

## 5. Sidebar reshaping (Story 4/5/6)

**Decision**: `AppShell.tsx`'s existing "Your communities" block (currently: every membership always listed, each with its own inline conditional "Admin" link) is reshaped, not replaced: it becomes a single line showing the active community's name (from the now-live-verified `account.activeCommunityId`), which expands via the same existing collapsible-list markup to show the *other* current memberships (FR-013/FR-015). The single "Admin" entry (FR-019) moves out of the per-row inline link and becomes one persistent nav entry, positioned directly above "Account," shown only when the active community's own membership row has `role === "ADMINISTRATOR"` — the same field this logic already reads today, just evaluated for one community (the active one) instead of once per row.

**Rationale**: Every underlying data source (`account.memberships`, `membership.role`) is unchanged; only which of them render, and where, changes to match FR-012–FR-021.
