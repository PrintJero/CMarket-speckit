# Research: Transaction Logging

## #1 No foreign-key relation from `Transaction` to `Listing` or `MessageThread`

**Decision**: `Transaction.listingId` is a plain string column with no Prisma relation and no database foreign-key constraint. A `listingTitle` snapshot (captured at creation) is stored alongside it. `Transaction` has no `threadId` column at all — the thread is consulted only at creation time to derive the recorder/counterpart pairing and is never referenced again afterward.

**Rationale**: FR-017 requires a log to survive its listing's deletion unaltered. 008-listing-messaging's `MessageThread`/`Message` cascade-delete with their listing (FR-015 there) — the opposite lifecycle a transaction log needs. A required FK with `onDelete: Restrict` (Prisma's default for a required relation) would instead **block** a listing's owner from ever deleting a listing that has a transaction log against it, silently contradicting 005-product-listings' FR-008 ("owner MUST be able to permanently delete their own listing"). The only way to keep both guarantees — the owner's unconditional delete right, and the log's permanence — is to not have a live constraint at all. This exact pattern already exists in this codebase: `AdministrativeAuditEntry.targetId` (009-platform-administration) is a plain string specifically because an audit entry must outlive the row it targets. `Transaction.listingId` follows the same precedent instead of inventing a new one.

**Alternatives considered**: `onDelete: SetNull` on a nullable `listingId` — rejected because it still requires a live FK relation (Prisma manages the constraint either way) and buys nothing over a plain string once a snapshot (`listingTitle`) is captured for display; a plain string is simpler and matches existing precedent. Cascading the transaction log with its listing — rejected outright; directly contradicts FR-017.

## #2 Counterpart and listing are derived from the thread, never accepted as separate client input

**Decision**: `recordTransaction(threadId, recorderAccountId)` takes only a `threadId` and the acting account. It loads the `MessageThread` (with its `listing`), determines the thread's `listingId`/`listingTitle`, and sets `counterpartId` to whichever of {`thread.buyerId`, `thread.listing.ownerId`} is *not* `recorderAccountId`. There is no `counterpartId` or `listingId` field in the request body at all.

**Rationale**: The spec's eligibility rule ("the recorder and counterpart must be the listing's owner and a buyer who messaged about it, in either direction") is naturally a property of a specific thread, not an independent fact to be asserted and then cross-checked. Accepting `counterpartId`/`listingId` as separate client-supplied fields would require validating that they actually match some existing thread anyway — deriving them from the thread directly collapses that validation into the lookup itself, removing an entire class of "claimed counterpart doesn't match the thread" bugs and rejecting anyone who isn't a participant of that thread by construction (if `recorderAccountId` is neither the thread's buyer nor its listing's owner, there is no "other side" to derive, and the call fails `not_a_participant`).

**Alternatives considered**: Accepting `listingId` + `counterpartId` directly (mirroring a generic "create a resource" shape) and separately verifying a matching thread exists — rejected as more surface area for the same guarantee, with no benefit since every real caller already has a specific thread open when they choose to record a transaction (the UI action lives on the thread page, research.md #7).

## #3 Live co-membership re-checked independently at creation and at confirmation

**Decision**: Both `recordTransaction()` and `confirmTransaction()` call `requireCommunityMembership()` (005-product-listings) for the acting account against `Transaction.communityId` (or, at creation time, the thread's listing's `communityId`) immediately before doing anything else — exactly like every other mutating call in `listingService.ts`/`messageService.ts`. Creation additionally requires the *derived counterpart's* current membership (not just the recorder's), since FR-002 is explicitly phrased as "both parties," unlike 008's messaging design (research.md #3 there), which deliberately checks only the acting caller.

**Rationale**: FR-002/FR-003 are explicit and symmetric: co-membership for *both* parties must hold at creation, and again at confirmation — independent of whether it held when the underlying thread was created. This is a deliberate difference from 008's "per-actor, not per-pair" messaging design: messaging is a live conversation where a departed member simply loses their own access (008 research.md #3), but a transaction log is a factual claim about *two* people, and Principle II ("cross-community leakage is treated as a security defect") together with Principle IV ("both parties MUST be verified as belonging to the same community before a transaction can occur or be logged between them") both name the pair, not one side of it.

**Alternatives considered**: Checking only the recorder's membership at creation (mirroring 008) and leaving the counterpart's membership to be discovered only when *they* try to confirm — rejected because it would let a log be *created* naming a counterpart who has already left the community, which is a more literal reading of FR-002's "verify both parties" than deferring half the check to a later, optional action.

## #4 Creation requires an ACTIVE community; confirmation tolerates SUSPENDED

**Decision**: `recordTransaction()` calls `requireCommunityMembership(recorderId, communityId)` and the counterpart-membership check with the default (`allowSuspended: false` — community must be `ACTIVE`). `confirmTransaction()` calls `requireCommunityMembership(counterpartId, communityId, { allowSuspended: true })`.

**Rationale**: 009-platform-administration's suspension model blocks "new listings or membership growth" while explicitly preserving activity in "existing threads" (its spec's own language). Creating a *new* transaction log is new data creation analogous to starting a new listing or a new message thread (008 research.md #4: a new thread requires an `ACTIVE` listing; only reply-in-an-existing-thread tolerates `SUSPENDED`). Confirming a log that already exists is analogous to replying in an existing thread — completing something already underway, not growing the community. This mirrors `sendMessageToListingOwner()`'s exact split between its top-level tolerant membership check and its ACTIVE-only new-thread branch (`src/server/services/messageService.ts`).

**Alternatives considered**: Requiring `ACTIVE` for both creation and confirmation — rejected as inconsistent with 009's own precedent that existing, already-underway activity (an existing thread's messages) remains available during suspension; an unconfirmed log the counterpart hasn't yet acted on is exactly that kind of already-underway activity from the recorder's side.

## #5 `paymentPath` ships as a single-value enum today

**Decision**: `enum TransactionPaymentPath { OFF_PLATFORM }` — one member. Every `Transaction` this feature creates has `paymentPath: OFF_PLATFORM`. No `IN_APP` value is added yet.

**Rationale**: FR-011 requires the log's *shape* (fields: recorder, counterpart, listing, community, timestamp, payment path, confirmation state) to support a future in-app path "without redesign" — it does not require building any in-app behavior now, and Principle VII explicitly forbids speculative functionality alongside the requested feature. This codebase's own enums (`MembershipRole`, `CommunityStatus`) were extended with new values by later features (`MEMBER` in 004, `SUSPENDED`/`ARCHIVED` in 009) rather than pre-declared unused ahead of time. Adding `IN_APP` later is a single additive Prisma migration (`ALTER TYPE ... ADD VALUE`) that touches no existing row and requires no change to `Transaction`'s other columns or to the confirmation state machine — which is exactly the "without redesign" guarantee FR-011 asks for, achieved by the column's *type* (a string-backed enum, trivially extensible) rather than by pre-building an unused value.

**Alternatives considered**: Declaring both `OFF_PLATFORM` and `IN_APP` now, with `IN_APP` simply unused until a future feature — rejected as speculative scope with no present consumer, against Principle VII and against this codebase's own established pattern for how enums grow.

## #6 `Transaction` rows are never hidden by a community's `operationalEpoch`

**Decision**: `Transaction.operationalEpoch` is stamped at creation from the community's current `operationalEpoch` (research.md #8 of 009's own plan — every per-community row does this), purely as a historical marker. Unlike `Listing`, `Membership`, `Invitation`, and `MessageThread`, a `Transaction` row is **never filtered out** of `listTransactions()`/`getTransaction()` based on a stale `operationalEpoch` — every transaction log the caller is a party to remains visible regardless of any later community restoration.

**Rationale**: 009's restoration model deliberately hides pre-restoration "operational activity" (listings, threads, memberships) because that activity belonged to a community state a restoration intentionally leaves behind ("all other prior members, listings, chats, invitations, and operational activity remain archived" — 009's own spec). A transaction log is different in kind: Constitution Principle IV calls it "the traceability layer" and "source of truth," and this feature's own spec.md explicitly states a confirmed log is retained forever specifically because it may feed a future reputation feature. Silently hiding a real, confirmed transaction after an unrelated administrative event (a different community's restoration) would contradict the one guarantee this entire feature exists to provide. Creation-time *eligibility* still uses the current epoch (research.md #2's thread lookup checks `thread.operationalEpoch === community.operationalEpoch`, exactly like `sendThreadMessage()`) — only a log that already exists is exempt from ever being hidden by a later epoch change.

**Alternatives considered**: Filtering `Transaction` by current epoch like every other entity, for mechanical consistency — rejected as a case where "be consistent with existing code" and "honor this feature's own non-negotiable purpose" conflict, and the latter wins by explicit constitutional and spec language.

## #7 The thread page is the primary surface; a standalone per-community log list is the fallback

**Decision**: The "record transaction" and "confirm" actions live on the existing thread detail page (`app/communities/[communityId]/threads/[threadId]/page.tsx`, 008-listing-messaging), since eligibility is thread-derived (research.md #2) and both participants are already looking at exactly the right context there. A separate `app/communities/[communityId]/transactions/` list + detail surface is added so a log remains reachable after its source thread is gone (FR-017 combined with FR-016 — see #1: the thread itself is deleted along with its listing, but the log is not).

**Rationale**: Putting the action anywhere else would require re-deriving "which thread, which listing, which counterpart" a second time in a different UI, duplicating research.md #2's derivation logic for no benefit. The standalone list is not optional scope creep — it is the only way FR-016 ("a log MUST be visible to both parties after it is created") can hold once FR-017 ("deleting the listing MUST NOT delete or alter any log that references it") has already made the thread-page path unreachable for that log.

**Alternatives considered**: A cross-community aggregated view mirroring 008's later `Chats`/`My listings` amendment — rejected as scope this feature's spec never requested; unlike 008's amendment (which was driven by a documented discoverability problem after shipping), nothing in 010's spec asks for cross-community aggregation, so building it now would be exactly the "speculative functionality" Principle VII prohibits. Revisit only if a real need is identified later, the same way 008 itself revisited its own initial scope.
