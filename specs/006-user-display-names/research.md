# Research: User Display Names

## 1. Where a federated display name is actually populated: `authOptions.events.linkAccount`, not the adapter's own `linkAccount()`

**Decision**: Populate `Account.displayName` (when the account doesn't already have one, per FR-005/FR-006) inside a new `events.linkAccount` handler in `authOptions` (`src/lib/auth/authConfig.ts`), reading `profile.name` from the event payload — not inside `buildPrismaAuthAdapter()`'s own `linkAccount()` method.

**Rationale**: Traced NextAuth v4's actual OAuth callback source (`node_modules/next-auth/core/lib/callback-handler.js`) rather than assuming: the adapter's `linkAccount(account: AdapterAccount)` is called as `linkAccount({ ...account, userId: user.id })` — it never receives the profile, only provider/providerAccountId/token fields, so FR-004's "populated from the provider's own profile name" is structurally impossible to implement inside the adapter's own `linkAccount()`. Immediately after every one of the three `linkAccount()` call sites in that file (brand-new user, existing-account-linked-while-signed-in, and — critically — the `getUserByEmail` auto-link path that is exactly FR-005/FR-006's scenario), core calls `await events.linkAccount({ user, account, profile })` and awaits it before ever calling `createSession()`. Tracing `core/routes/callback.js` confirms the `profile` this event receives is the *mapped* profile (`provider.profile()`'s output — `{ id, name, email, image }`, matching `GoogleProfile.name` 1:1 via `GoogleProvider`'s own mapping), not GoogleÊ¼s raw payload, and confirms this happens before the session cookie is written back to the browser. One hook point therefore uniformly covers all three linking paths spec.md enumerates (brand-new account, link to an existing unverified account, link to an existing verified account) with no per-path branching required beyond the existing "does this account already have a displayName?" check FR-005/FR-006 already specify.

**Alternatives considered**: A custom `signIn` callback — rejected after tracing `core/routes/callback.js`: for the `getUserByEmail` auto-link case specifically, `signIn` fires *before* `callbackHandler()` resolves which existing `Account` the email matches, so the callback's `user` parameter does not yet carry our internal `Account.id` for that case; using it would mean re-implementing the email-lookup a second time, duplicating logic the adapter already owns. Extending the adapter's `linkAccount(account: AdapterAccount)` signature to also carry the profile — not possible; NextAuth core controls that call's argument shape, not the adapter.

## 2. Mocking Google for a real end-to-end callback test: a standalone mock-server process outside `app/`, not a Next.js route of any kind

**Decision (revised, 2026-07-17, third round)**: The mocked Google OAuth boundary is a small, standalone Node HTTP server — `scripts/mock-google-oauth-server.ts`, run via `tsx` (the same devDependency 003's `scripts/create-community.ts` already uses), started as a *second* Playwright `webServer` entry alongside the existing Next.js dev server, listening on its own port (`GOOGLE_OAUTH_MOCK_URL`, e.g. `http://localhost:4310`, set in `.env.test`). It is **not** a Next.js route under `app/` in any form. When `GOOGLE_OAUTH_MOCK_ENABLED === "true"`, `authConfig.ts` points `authorization`/`token`/`userinfo` at that server's URL (`wellKnown` omitted); otherwise it registers the real `GoogleProvider(...)` unchanged. The server implements just enough of the authorization-code flow to be indistinguishable, from NextAuth's perspective, from the real Google endpoints: `GET /authorize` redirects to the given `redirect_uri` with a fixed `code` and the caller's own `state` echoed back; `POST /token` returns a fixed opaque access token; `GET /userinfo` returns a fixed, Google-profile-shaped JSON body (`sub`, `email`, `email_verified`, `name`, `picture`) from a small in-memory fixture keyed by the access token, so a single Playwright run can exercise multiple distinct profiles (with a name, and — Edge Cases — without one). Its request-handling logic is written as plain, exported functions (`buildAuthorizeRedirect()`, `handleTokenRequest()`, `handleUserinfoRequest()`) with a thin `http.createServer()` wrapper that only binds a port when the file is the actual process entry point (`import.meta.url` matching the invoked script path) — so a test can import and call the handler functions directly without starting a real listener, the same "call the exported function directly, no server needed" shape `tests/contract/test_operator_panel.ts` already uses for a Next.js route handler.

**Why this replaces the second-round design (mock routes under `app/api/test/mock-google-oauth/`, excluded from a production build via `next.config.ts`)**: that design fixed the *trigger* problem (an npm `prebuild` script cannot reliably observe `NODE_ENV=production`; `next.config.ts` can) but left a fatal *consequence* unaddressed, caught by this round's review: the guard's condition was "`NODE_ENV === "production"` AND the mock-oauth directory exists on disk" — and that directory lives in the repository, checked in, with nothing anywhere that ever removes it. Every real production build (Dokploy, CI, anywhere) checks out the same repository and therefore always finds the directory, so the guard would fire on **every** production build, permanently, with no specified path to a successful one. `npm run build` has been part of this project's own verification loop since 002 (every prior feature's Polish phase runs it); a guard that unconditionally breaks it is not a guard, it is a landmine — "the predictable outcome is that the first real deploy attempt fails ... and the guard gets commented out" (reviewer, 2026-07-17, third round). The fix is not a better trigger for excluding the routes from the build — it is removing the reason a build-time exclusion is needed at all, per that same review's option (b): host the mock boundary somewhere Next.js's own build never looks. Next.js's routing is entirely filesystem-driven from `app/` (or `pages/`); a file that never lives there is never part of the route tree, in development, in the test run, or in a production build — there is nothing to exclude because there was never anything included. This also means `src/lib/build/assertTestOnlyRoutesExcluded.ts`, its `next.config.ts` wiring, and its dedicated unit test are all removed as unnecessary — the guarantee they existed to provide is now true unconditionally, by construction, not by a check that has to run and pass at the right moment.

Because the mock server is never started by anything the production deploy path invokes (`npm run build`, `next build`, `next start` — none of these execute `scripts/mock-google-oauth-server.ts`; only Playwright's test-only `webServer` entry does), it needs no environment-variable gate of its own to stay out of production — unlike 003's operator panel or this feature's own `PATCH /api/account/display-name`, there is no code path in the shipped application that could ever reach it, gated or not. The remaining, genuinely load-bearing gate is on the *other* side of the boundary — `authConfig.ts`'s choice of which provider config to register — and that gate is real production code, shipped and running in every environment, so it keeps full mitigation treatment:

1. **Runtime gate in `authConfig.ts`'s provider selection.** `authOptions.providers` is built by checking `process.env.GOOGLE_OAUTH_MOCK_ENABLED === "true"`: only then does it construct an `OAuthConfig` pointing at `GOOGLE_OAUTH_MOCK_URL`; otherwise it is the real `GoogleProvider(...)`, exactly as before this feature. Since `GOOGLE_OAUTH_MOCK_ENABLED` defaults unset/false (`.env.example`), production always gets the real provider regardless of whether the mock server happens to be running anywhere reachable.
2. **A static guard test**, in the spirit of `tests/unit/test_community_creation_not_networked.ts`, parses `authConfig.ts`'s source and asserts every reference to `GOOGLE_OAUTH_MOCK_URL`/the mock provider construction is textually nested inside a branch conditioned on `GOOGLE_OAUTH_MOCK_ENABLED` — narrower in scope than the second round's version (no more route files to check, since none exist), kept as a regression guard on the *shape* of this one remaining gate.
3. **A behavioral test — this round's second reviewer finding, previously missing.** Mitigation 1 had only ever been static-checked, the exact gap just closed for the (now-removed) routes: "a guard can be present and wrong." `tests/unit/test_auth_google_provider_selection.ts` forces a fresh module evaluation (`vi.resetModules()` + dynamic `import()`) of `authConfig.ts` under both env states and asserts the *actual resulting* `authOptions.providers[0]` object: with `GOOGLE_OAUTH_MOCK_ENABLED` unset, `provider.wellKnown` equals Google's real discovery URL (`https://accounts.google.com/.well-known/openid-configuration`) and no `GOOGLE_OAUTH_MOCK_URL` value appears anywhere in `provider.authorization`/`.token`/`.userinfo`; with it set to `"true"`, `provider.wellKnown` is absent and all three endpoint URLs are prefixed with `GOOGLE_OAUTH_MOCK_URL`. This is what proves the gate *works*, not merely that its source *exists* — the same static-vs-behavioral pairing this feature already applies elsewhere (research.md's prior revision), now correctly aimed at the one gate that's still real production code.
4. **Documented at the point of configuration.** `GOOGLE_OAUTH_MOCK_ENABLED=""` and `GOOGLE_OAUTH_MOCK_URL=""` are added to `.env.example`, with an explicit comment that neither must ever be set in a real deployment, mirroring `OPERATOR_PANEL_ENABLED`'s existing entry.
5. **The mock server's own request-handling logic is unit-tested directly** (`tests/unit/test_mock_google_oauth_server.ts`, importing `buildAuthorizeRedirect()`/`handleTokenRequest()`/`handleUserinfoRequest()` with no port bound) — ordinary correctness testing for test infrastructure, not a security mitigation, since nothing about its own behavior matters once it is unreachable from production by construction.

**Verifying "no route to exclude" is real, in both directions**: since there is no build-time toggle anymore (the server's absence from `app/` is unconditional, not something a flag turns on or off), the second round's "build must fail with the routes present, succeed with them absent" framing doesn't map onto this design directly — there is only ever one state. What must instead be verified, and is verified two ways: (a) `npm run build` succeeds unconditionally, exactly as it always has since 002 (tasks.md's Polish phase already runs this on every feature; no special-casing is added or needed) — there is nothing in this feature that can make it fail; (b) after a real build (`npm run build && npm start`), requesting `/api/test/mock-google-oauth/authorize` (or any path under that prefix) against the running **Next.js application** (port 3000, not the mock server's own port) returns Next's ordinary `404` — proving structurally that no such route was ever registered there, in any build, not merely that a check happened to catch it this time. The mock server's own behavior (that it *does* work when deliberately started) is what the real end-to-end Playwright test (`tests/integration/test_google_display_name.spec.ts`) already proves, via Playwright's second `webServer` entry.

**Rationale**: `node_modules/next-auth/core/lib/oauth/client.js` confirms NextAuth only performs live `.well-known` discovery when `provider.wellKnown` is set; when it's omitted, it builds the OAuth `Issuer` directly from `provider.authorization.url` / `provider.token.url` / `provider.userinfo.url` with no network call to Google at all — this is what makes fully offline mocking possible without patching `next-auth` itself, regardless of where the mock server lives. Playwright natively supports an array of `webServer` entries (one per process to start/wait-on before tests run), so a second entry for this server is not a novel mechanism, just an additional, already-supported config entry.

**Alternatives considered**: Driving Google's real consent screen with a fixed test-user allowlist (Google OAuth "Testing" publishing status) — rejected per spec.md's own reasoning: Google blocks automated browsers, and a real network dependency in CI reintroduces exactly the flakiness/unavailability risk that motivated mocking at the OAuth boundary in the first place. A generic Node-level HTTP-mocking library (e.g., intercepting global `fetch`) injected into the running `next dev` server process — rejected: more invasive to the app's own bootstrap than a small, separately-started script. **Hosting the mock endpoints as ordinary Next.js API routes under `app/`, excluded from a production build via a `next.config.ts`-enforced guard — this feature's own second-round decision, now retracted**: it solved the wrong half of the problem (a reliable trigger) while leaving the other half (a state in which the trigger's condition is ever *false* for a real production build) completely unspecified, since nothing removed the directory the guard checked for. **A second, standalone mock-server process — this feature's own first-round rejection, now reversed**: originally rejected as "adds a second port and a second `webServer` entry to coordinate for a need three routes already satisfy" — that cost assessment did not yet know the alternative (routes under `app/`) had no viable path to a successful production build at all. Weighed against "permanently breaks every production deploy unless a human remembers a manual step," one extra `webServer` entry and one extra port are the clearly smaller cost; the earlier rejection is corrected here rather than left standing.

## 3. Enforcing FR-008 "regardless of client": one precondition inside `createListing()` itself, no new request field

**Decision**: `createListing()` (`src/server/services/listingService.ts`) gains a single precondition, checked immediately alongside its existing membership check: if the calling account's `displayName` is `null`, reject with a new `{ ok: false, reason: "display_name_required" }` — independent of anything else in the request. No new field is added to `createListing()`'s existing input shape or to `POST /api/communities/{communityId}/listings`'s request body.

**Rationale**: Every caller — the listing-creation page's form, and any direct API request — already passes through this one function; a client-side-only prompt cannot be the enforcement point, since FR-008 explicitly requires the guarantee to survive a direct request that skips the form entirely. Making the check a precondition of `createListing()` itself, rather than accepting a `displayName` parameter to set-and-create in one call, keeps the create-listing contract exactly as it is today (Principle VII) and reuses the account-settings endpoint (contracts.md) as the *only* place a display name is ever written, rather than introducing a second write path with its own validation rules to keep in sync with FR-012. The listing-creation page, when it detects (from the signed-in account's own current payload) that `displayName` is `null`, shows an inline "Display name" field alongside the listing form; on submit it calls the account-settings endpoint first, and only proceeds to `POST .../listings` once that succeeds. If a caller skips that step entirely, `createListing()` still rejects it.

**Alternatives considered**: Accepting an optional `displayName` field directly in the create-listing request and setting it transactionally alongside the listing — rejected: it would create a second code path capable of writing `Account.displayName`, alongside the account-settings endpoint, each needing to enforce FR-012's validation identically; a single write path is simpler to keep correct. Enforcing only in the page/form — rejected outright per FR-008 and the reviewer note that this codebase already carries a precedent for exactly this class of gap (an authorization/precondition check present in a page but not the service it calls).

## 4. Rendering: a shared `resolveDisplayName()` helper, mirroring the existing `formatListingPrice()` precedent

**Decision**: A new `src/lib/formatting/displayName.ts` exports `DISPLAY_NAME_PLACEHOLDER = "A member"` and `resolveDisplayName(displayName: string | null): string` (returns the placeholder when `null`, the trimmed value otherwise). `listListings()` and `getListing()` (`listingService.ts`) are extended to return the owner's raw `ownerDisplayName: string | null` (never resolving the placeholder server-side, exactly as they already return `coverPhotoId: string | null` and let the page decide presentation) — the feed page and detail page both call `resolveDisplayName()` before rendering.

**Rationale**: This is the identical shape of decision 005's amendment already made for `formatListingPrice()`/`LISTING_CURRENCY` (one shared formatter, not a hardcoded value duplicated per page component) — reusing an established, working pattern in this same codebase rather than inventing a new one (Principle VII). Keeping the raw `string | null` in the service's return shape (rather than resolving the placeholder server-side) matches `coverPhotoId`'s existing precedent and keeps the service layer's contract about *data*, not *presentation*.

**Alternatives considered**: Resolving the placeholder inside the service functions themselves — rejected for consistency with `coverPhotoId`'s existing raw-nullable precedent, and because SC-004/SC-005's tests need to distinguish "no display name" from "the literal placeholder string" at the data layer (e.g., confirming a federated link did *not* overwrite an existing name is clearer against the raw stored value).

## 5. Account settings surface: one new page, one new endpoint, reused by both User Story 2 and User Story 4

**Decision**: `app/account/page.tsx` (a new, top-level, signed-in-only page — not nested under `/communities/{id}`, since a display name is account-level per FR-014) renders the current display name and an edit form. `PATCH /api/account/display-name` (new route, body `{ displayName: string }`) is the *only* place `Account.displayName` is ever written; it derives the target account exclusively from the caller's own session (`getCurrentAccount()`), never from a client-supplied account id — this is what makes FR-002's "no other account may change it" hold by construction rather than by an authorization check that could be gotten wrong. The listing-creation flow (decision #3) calls this same endpoint as its first step when a display name is still needed. The home page's sidebar (`app/page.tsx`) gains a link to `/account`, since User Story 4 requires the account holder to actually be able to reach this view "in a single, direct step," not merely at a guessable URL.

**Rationale**: One endpoint, reused by both stories, is simpler than a dedicated "set display name during listing creation" endpoint plus a separate "edit my display name" endpoint that would need identical validation (FR-012) kept in sync. Deriving the target account solely from the session cookie (never a request parameter) is the same pattern this codebase already uses everywhere an account acts on its own data (e.g., `sign-out` reads the session cookie, never an account id from the client).

**Alternatives considered**: A modal/dialog embedded in the listing-creation page instead of a dedicated account settings page — rejected: User Story 4 needs a durable, revisitable place to view/edit the name independent of ever creating a listing again, and a modal-only implementation would leave that story unmet.

## 6. Data model: `Account.displayName`, nullable, no new entity

**Decision**: Add `displayName String?` to the existing `Account` model in `prisma/schema.prisma` (nullable, no default — absent means `null`, not an empty string). No new table. Migration name: `add_account_display_name`.

**Rationale**: FR-001/FR-014 describe a single, optional, account-level attribute — the simplest possible modeling, consistent with Principle VII and with how this schema already models similarly-shaped optional attributes (e.g., `Account.passwordHash String?`).

**Alternatives considered**: A separate `Profile` table — rejected as speculative given this feature's explicit exclusion of avatars, bios, and public profile pages (FR-016); a single nullable column is the entire data requirement today.
