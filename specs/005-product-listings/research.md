# Research: Product Listings

## 1. Photo storage: bytes in PostgreSQL (`Bytes`/`bytea`), not object storage or local disk

**Decision**: `ListingPhoto` stores the raw image bytes directly in Postgres via Prisma's `Bytes` type, alongside `mimeType` and `sizeBytes`. Photos are served by a dedicated route (`GET /api/communities/[communityId]/listings/[listingId]/photos/[photoId]`) that streams the bytes with the stored `mimeType` as `Content-Type`. Uploads are accepted as `multipart/form-data` in the add-photo route handler, parsed via Next.js's built-in `request.formData()` — no new dependency. `communityId` stays in the path on this route exactly as on every other listing route (research.md #5) — a photo is never reachable except through its own community's scope.

**Rationale**: This codebase provisions exactly one storage system today — PostgreSQL via Prisma (constitution's Stack constraint) — and no Dockerfile/app-container config exists yet to confirm the deployed environment has persistent local disk across redeploys. Storing photo bytes in the already-decided, already-backed-up database means photo durability is covered by the constitution's existing "automated database backups MUST exist, and restoration MUST be verified" requirement with no second backup story, no new environment variable, and no new dependency — the simplest option that satisfies FR-003, per Principle VII. Reasonable caps (below) keep row/page bloat bounded.

**Alternatives considered**: An S3-compatible object storage SDK — rejected: introduces a new paid/external dependency, new credentials/env vars, and a second durability story to verify, for a feature whose spec never asked for CDN-grade media delivery. Local filesystem (`public/uploads/`) — rejected: this repository has no Dockerfile/volume configuration confirming the production container's disk survives a redeploy; silently losing sellers' photos on every deploy is worse than the bytea-in-Postgres tradeoff. A managed upload service (UploadThing, Cloudinary) — rejected for the same reason as S3: a new external dependency and account/credential the spec never requested, mirroring this project's existing preference for vendor-agnostic, dependency-free defaults (`sendEmail()`'s `ConsoleEmailTransport` default, `EMAIL_WEBHOOK_URL` pattern).

**Caps** (Principle VII: reasonable, undocumented-but-necessary defaults, not speculative configurability): max 5MB per photo, max 6 photos per listing, accepted MIME types `image/jpeg`, `image/png`, `image/webp` only. Oversized/wrong-type uploads are rejected with a clear error; nothing about these caps is user-configurable.

## 2. Authorization: reuse the existing per-request membership-lookup pattern, add one new "any role" variant

**Decision**: `listingService.ts` defines `requireCommunityMembership(accountId, communityId): Promise<boolean>` (any role — `ADMINISTRATOR` or `MEMBER`) for create/view actions, alongside reusing the existing `requireCommunityAdministrator()` from `src/server/services/invitationService.ts` for the administrator-moderation path (FR-009). Ownership checks (`listing.ownerId === accountId`) are plain equality checks inline in each service function — no new abstraction.

**Rationale**: `requireCommunityAdministrator()` already exists and does exactly what FR-009's moderation gate needs — reusing it (research.md #8 of 004-invitations-membership) avoids duplicating the identical `prisma.membership.findUnique({ where: { accountId_communityId: ... } })` lookup a third time. `requireCommunityMembership()` is the same lookup with a looser role check (`membership !== null` instead of `role === "ADMINISTRATOR"`), matching this codebase's established convention (004 research.md #8: a small shared function in the service layer, not a framework-level middleware — there is still no `middleware.ts` in this project and no reason to introduce one for a third feature's two call sites).

**Alternatives considered**: A shared cross-feature `authService.ts` — rejected: only two functions (`requireCommunityMembership`, `requireCommunityAdministrator`) exist across two features; introducing a shared module for two callers is exactly the premature abstraction Principle VII warns against. Importing `requireCommunityAdministrator` from `invitationService.ts` was chosen over duplicating it, since a second near-identical copy is the concrete cost of *not* reusing it.

## 3. Listing lifecycle: `status` enum with two values, hard delete distinct from pause

**Decision**: `ListingStatus` is a native Prisma enum with exactly `ACTIVE` and `PAUSED` (FR-004). Pausing/reactivating is an `UPDATE` of the `status` column; both are idempotent (`updateMany` guarded by the expected prior status is unnecessary here — a plain `update` to the target status is safe and idempotent by construction, since setting `status: "PAUSED"` on an already-`PAUSED` row is a no-op write, not a race-prone state transition like invitation consumption was). Deletion (FR-008) is `prisma.listing.delete`, cascading to `ListingPhoto` via `onDelete: Cascade` — mirroring 004 research.md #3's precedent (`Membership` revoke = hard delete, not a soft-delete flag) for the same reason: nothing in this feature's scope needs a historical "was once deleted" record, and a soft-delete flag would require every future listing query to remember to filter it out.

**Rationale**: Unlike invitation consumption (research.md #5 of 004) or the last-admin count (same doc), pause/reactivate has no concurrent-race safety property to prove — two administrators concurrently pausing the same listing both converge on `PAUSED`, which is the correct outcome either way (no lost update, no invariant to violate). This means the extra `updateMany`/count-check machinery 004 needed is not needed here; a plain conditional `update` keyed on `id` (and, for authorization, on owner/community) is sufficient and simpler (Principle VII).

**Alternatives considered**: A `DELETED` value on the same `ListingStatus` enum instead of a hard delete — rejected: the spec (FR-008, User Story 4) explicitly separates "delete" (permanent, owner-only) from "pause" (reversible, owner-or-admin), and conflating them into one enum would let an admin's pause authority accidentally reach the delete-equivalent state, violating FR-009's "MUST NOT extend to... deleting it."

## 4. Testing stack: Vitest (contract/unit) + Playwright (integration), same as 004

**Decision**: Follow 004-invitations-membership's stack exactly: `tests/contract/test_listings.ts` (Vitest, calling `createListing()`/`updateListing()`/`pauseListing()`/`reactivateListing()`/`deleteListing()`/`addListingPhoto()`/`removeListingPhoto()` directly against the real test Postgres DB), `tests/integration/test_listing_flow.spec.ts` (Playwright, driving the real create/edit/pause/delete UI and the community-scoped listing feed).

**Rationale**: "Product listing" is one of Principle VIII's explicitly named critical flows — the same non-negotiable test-first obligation 004 already carried, and this codebase already has both layers wired (real test Postgres container, `EMAIL_TEST_CAPTURE`-equivalent not needed here since listings send no email). No new test infrastructure is required.

**Alternatives considered**: None — this is a direct continuation of an already-established, working pattern; introducing a different test stack for this feature would itself be an unjustified deviation.

## 5. Route/page structure: extend the existing `/communities/[communityId]/` convention

**Decision**: Listings live under `app/communities/[communityId]/listings/` (browse — member-only; create — member-only) and `app/communities/[communityId]/listings/[listingId]/` (detail/edit — owner-only edit, member-only view). API routes mirror this: `app/api/communities/[communityId]/listings/route.ts` (`GET` list, `POST` create), `app/api/communities/[communityId]/listings/[listingId]/route.ts` (`GET` one, `PATCH` edit, `DELETE`), `.../[listingId]/pause/route.ts` and `.../[listingId]/reactivate/route.ts` (`POST`, owner-or-admin), `.../[listingId]/photos/route.ts` (`POST` add), `.../[listingId]/photos/[photoId]/route.ts` (`GET` stream bytes, `DELETE` remove).

**Rationale**: 004 already established `app/communities/[communityId]/admin/` as this codebase's first end-user-facing, community-scoped route group; nesting `listings/` under the same `[communityId]` segment keeps every listing URL self-evidently community-scoped (Principle II — FR-011) and reuses the exact dynamic-route-param convention (`{ params: Promise<{ communityId: string }> }`) already in place from 004's routes.

**Alternatives considered**: A top-level `/listings/[listingId]` route with `communityId` only as a query param or body field — rejected: makes it easier to *forget* the community-scoping check on some future call site, exactly the retrofitted-tenancy risk the constitution's Tenancy constraint warns against ("designed with community scoping as a first-class dimension, not retrofitted later"). Keeping `communityId` in the URL path itself makes every route handler's signature carry the scope by construction.
