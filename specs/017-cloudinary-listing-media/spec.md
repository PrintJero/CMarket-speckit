# Feature Specification: Cloudinary Listing Media Integration

**Feature Branch**: `017-cloudinary-listing-media`

**Created**: 2026-08-06

**Last revised**: 2026-08-06 — delivery architecture changed from public Cloudinary URLs rendered through Next.js Image to **authenticated CMarket proxy routes**. Every `next/image`, `remotePatterns`, image-loader, `srcset`, and no-raw-`<img>` requirement is removed. The maintainer sign-off previously required for public delivery is removed with it.

**Amended 2026-08-06** (two corrections, FR-107–FR-109 added):

1. **Upload exposure is distinguished from delivery exposure.** The earlier blanket claim that no Cloudinary hostname, URL, or public ID ever reaches the browser was incompatible with the accepted direct browser-to-Cloudinary upload architecture, which requires the browser to receive an upload endpoint, API key, timestamp, signature, and server-generated public ID. The prohibition now applies precisely to **delivery and listing reads**, where it belongs.
2. **Cached images must be revalidated before reuse.** `Cache-Control: private, max-age=300` is replaced by `private, no-cache` with `ETag` retained, and authorization must precede a `304` as strictly as it precedes a `200`. This closes two real holes the TTL left open: leaving a community, or switching accounts in the same browser, previously reused authorized bytes for up to five minutes without any check.

**Status**: Draft

**Input**: User description: "Replace CMarket's current listing-image implementation completely with a single Cloudinary-backed media system. Cloudinary will store and deliver the actual image files, while PostgreSQL will store only Cloudinary asset references and listing presentation metadata. It is acceptable to change the Prisma schema and apply a destructive migration. Do not preserve, migrate, import, render, or maintain compatibility with images stored through the previous image method. Existing listings that lose legacy images may become image-less and use the existing no-image placeholder. Do not maintain two image systems in parallel.

Do not use or display the Cloudinary Upload Widget. Build a custom CMarket multi-image uploader inside the existing create-listing and edit-listing forms. Members must be able to select multiple images at once, preview them, remove them, rearrange them, choose a cover image, see individual upload progress, and retry individual failures. Upload files directly from the browser to Cloudinary using short-lived signed parameters generated by the authenticated CMarket server. Never expose the Cloudinary API secret.

Support up to eight photos per listing. Accept JPEG, PNG, and WebP images up to 10 MB each. Use bounded upload concurrency, with three simultaneous uploads as the default. Store stable Cloudinary identifiers, width, height, format, order, cover state, and listing association in PostgreSQL. Do not store image bytes, blobs, base64 data, or durable local container file paths.

Cloudinary images must appear correctly in community feeds, listing detail, public profiles, Account, My listings, FOR_SALE and WANTED surfaces, transaction listing context, and every existing surface that displays listing media.

The integration must preserve existing listing ownership, membership, authorization, community isolation, status, stock, price, wanted-post, cover-photo, and listing-editing rules. Videos, avatars, chat attachments, image moderation, notifications, cropping, and the Cloudinary Upload Widget are out of scope."

**Revision input**: "Next.js Image is not a required part of this feature. Use authenticated CMarket image proxy routes instead of exposing Cloudinary delivery URLs directly to browsers. The browser must request images through a CMarket route such as `/api/communities/{communityId}/listing-photos/{photoId}`. For every image request the route must validate the session, validate current membership, verify the photo belongs to a listing in that community, return 403/404 using existing isolation behavior when invalid, fetch the appropriate image from Cloudinary, and return the bytes without exposing the Cloudinary source URL. A user who knows only the CMarket proxy URL must still require a valid current session and membership. Rendering may use a normal `<img>` element or a small reusable CMarket component. Support predefined image variants rather than arbitrary client-controlled dimensions. Use private browser caching. Keep the existing direct signed browser-to-Cloudinary upload architecture — the proxy applies only to delivery."

## Current State (baseline being replaced)

Recorded so the hard cutover in User Story 7 has a concrete target. This is the state observed in the repository at spec time, not a design proposal:

- Listing photo bytes are stored **inside PostgreSQL** on the listing-photo record, alongside a MIME type and an integer position.
- Photo bytes are served by an **authenticated, membership-gated** CMarket read endpoint at `/api/communities/{communityId}/listings/{listingId}/photos/{photoId}` — a caller who is not a current member of the listing's community is refused. **This access model is preserved by this feature**; only the byte source changes, from a PostgreSQL column to Cloudinary.
- The current per-listing photo ceiling is **six**; this feature raises it to eight.
- Cover selection is a single-cover reference held on the listing, cleared or reassigned when the referenced photo is removed. Unchanged by this feature.
- Listing media is rendered with plain `<img>` elements. **This remains acceptable** — no rendering-library migration is part of this feature.
- Exactly **three** surfaces render listing media today: the community main view, the community listings (discovery) view, and the listing detail gallery. The listing card placeholder reads "No photo".
- Account, My listings, public profiles, and transaction listing context **do not display listing media today**, and this feature does not add it.
- The create/edit listing form uploads photos one file at a time after the listing is saved, with no preview, no progress, no reorder, no cover control, and no per-file error recovery.
- There is no concept of an image variant: a card and the detail gallery both fetch the same full-size bytes and scale them with CSS.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Upload multiple listing images through CMarket's interface (Priority: P1) 🎯 MVP

A member creating or editing a listing can select several images in one action and manage them through a custom CMarket uploader. The member never sees Cloudinary's Upload Widget or any Cloudinary-branded upload interface.

**Why this priority**: The main purpose of the feature is to provide reliable cloud-hosted listing media while CMarket keeps complete control of the user experience.

**Independent Test**: Open a create-listing form, select several valid images at once, and confirm all files appear as previews, upload successfully through the custom uploader, and become associated with the saved listing.

**Acceptance Scenarios**:

1. **Given** an authenticated current member who can create a listing, **When** they select between one and eight valid images in one file-selection action, **Then** every selected image appears in the custom CMarket preview area.
2. **Given** several selected images, **When** the uploader renders, **Then** each image shows its own preview and upload state without loading or displaying the Cloudinary Upload Widget.
3. **Given** a selected image that has not been saved, **When** the member removes it, **Then** it disappears from the pending media set without affecting the other selected images.
4. **Given** eight images are already selected or associated, **When** the member attempts to add another, **Then** the additional file is rejected with a clear maximum-photo message.
5. **Given** an unsupported file type or a file larger than 10 MB, **When** it is selected, **Then** that file is rejected with a file-specific validation error naming which file failed and why.
6. **Given** a mobile viewport, **When** the member selects multiple photos from the device gallery, **Then** the uploader remains usable without horizontal overflow.
7. **Given** a listing form with no selected images, **When** the existing listing rules allow image-less listings, **Then** the listing can still be saved and uses the existing no-photo placeholder.

### User Story 2 - Arrange photos and choose a cover image (Priority: P1)

A listing owner can control the order in which photos appear and choose which photo represents the listing in cards and feeds.

**Why this priority**: Multiple images are useful only when the seller can determine which image appears first and how the gallery is presented.

**Independent Test**: Select several images, reorder them, choose a cover, save the listing, and confirm the listing card uses the selected cover while the detail gallery follows the saved order.

**Acceptance Scenarios**:

1. **Given** several selected photos with no explicit cover, **When** the listing is saved, **Then** the first photo in the saved order becomes the cover.
2. **Given** several photos, **When** the member selects a different cover, **Then** that photo becomes the only cover without removing or duplicating any photo.
3. **Given** several selected or existing Cloudinary photos, **When** the member changes their order, **Then** the saved listing displays them in that same order.
4. **Given** upload requests finish in a different order from the user's chosen order, **When** the listing is saved, **Then** the chosen display order is preserved.
5. **Given** the current cover is removed while other photos remain, **When** changes are saved, **Then** the first remaining photo becomes the cover unless another cover was explicitly selected.
6. **Given** all photos are removed, **When** the listing remains valid under existing rules, **Then** it uses the existing no-photo placeholder.
7. **Given** photos are reordered on a touch-only device, **When** the member changes the order, **Then** reordering is achievable without a drag gesture that touch input cannot perform.

### User Story 3 - See upload progress and recover from failures (Priority: P1)

A member receives clear progress feedback for each selected image and can retry or remove a failed upload without losing successful uploads.

**Why this priority**: Members may upload from unstable mobile connections. One failed file should not force the entire batch to restart.

**Independent Test**: Upload several images, force one upload to fail, and confirm successful files remain complete while the failed file offers Retry and Remove actions.

**Acceptance Scenarios**:

1. **Given** several valid images, **When** uploading begins, **Then** each image displays an individual state such as waiting, uploading, uploaded, or failed.
2. **Given** some images upload successfully and one fails, **When** the failure occurs, **Then** successful images remain successful and are not uploaded again.
3. **Given** a failed image, **When** Retry is selected, **Then** only that image is retried.
4. **Given** a failed image, **When** Remove is selected, **Then** it is removed and the remaining valid images can still be saved.
5. **Given** one or more images are still uploading, **When** the member attempts to submit the listing, **Then** submission is prevented and the uploader explains that uploads are still in progress.
6. **Given** all remaining images have uploaded successfully, **When** the listing is submitted, **Then** the listing and its media associations are saved without duplicate photo records.
7. **Given** the upload authorization expires before one waiting file starts, **When** that file uploads, **Then** it requests fresh authorization without restarting completed uploads.
8. **Given** more than three files are selected, **When** uploading begins, **Then** at most three uploads are in flight at once and the remainder wait their turn.

### User Story 4 - Display images through authenticated CMarket delivery (Priority: P1)

Members browsing CMarket see Cloudinary-stored listing media, fetched through an authenticated CMarket route that re-checks session and membership on every request. The browser never learns where the file actually lives.

**Why this priority**: The storage integration is incomplete unless every listing surface reliably displays media, and delivery is the point at which community isolation is either preserved or broken.

**Independent Test**: Open a listing card and listing detail on desktop and mobile, confirm images render with the correct cover and gallery order, then confirm no Cloudinary delivery URL, authenticated source URL, or persisted Cloudinary identifier appears in the page source, listing responses, or image-delivery responses, and that the same image request fails without a session or without membership.

**Acceptance Scenarios**:

1. **Given** a listing with a cover image, **When** it appears in a feed or listing card, **Then** the cover renders from a CMarket image route, not from a Cloudinary URL.
2. **Given** a listing with several images, **When** its detail page opens, **Then** images appear in their saved order.
3. **Given** any rendered listing page or listing read response, **When** its HTML, JSON, and image-delivery responses are inspected, **Then** no Cloudinary delivery URL, authenticated source URL, or persisted Cloudinary identifier is present.
4. **Given** an image request, **When** the route responds, **Then** it streams the image bytes itself and does **not** redirect the browser to Cloudinary.
5. **Given** an unauthenticated caller, **When** an image route URL is requested directly, **Then** the request is refused and no bytes are returned.
6. **Given** an authenticated account that is not a current member of the requested community, **When** an image route URL is requested, **Then** the request is refused using the project's existing isolation behavior.
7. **Given** an image belonging to a listing in a different community from the one named in the request path, **When** the request is processed, **Then** it is refused as not found.
8. **Given** a valid request from a current member, **When** the image is returned, **Then** the response carries private, must-revalidate caching directives and is not stored in any shared cache that would skip membership validation.
9. **Given** a browser holding a cached image and sending a conditional request, **When** the caller has since left the community or signed in as a different account, **Then** the request is refused and no `304` is returned.
10. **Given** a browser holding a cached image and sending a conditional request, **When** the caller is still authorized and the image is unchanged, **Then** a `304` is returned only after authorization has passed.
11. **Given** a request naming a predefined variant such as thumbnail, card, or detail, **When** it is processed, **Then** the correspondingly sized image is returned.
12. **Given** a request supplying an arbitrary width, dimension, or transformation string, **When** it is processed, **Then** the unrecognized value is rejected or ignored in favour of a server-defined variant, and never passed through to the storage provider.
13. **Given** stored width and height metadata, **When** an image renders, **Then** the rendered element reserves space in the correct proportion and avoidable layout movement is prevented.
14. **Given** different viewport sizes, **When** the same photo renders, **Then** it preserves its natural aspect ratio, is not distorted, and causes no horizontal overflow.
15. **Given** a listing detail gallery, **When** it renders, **Then** non-cover gallery images are lazily loaded.
16. **Given** a listing image, **When** it renders, **Then** it has meaningful alternative text derived from listing context rather than a filename or internal identifier.
17. **Given** a listing without photos, **When** it appears anywhere in CMarket, **Then** the existing no-photo placeholder is shown.

### User Story 5 - Securely authorize browser uploads (Priority: P1)

Cloudinary uploads are authorized by CMarket without exposing unrestricted credentials or allowing unauthorized asset associations. Upload remains a direct browser-to-Cloudinary transfer; only delivery is proxied.

**Why this priority**: Direct browser uploads must not expose the API secret or let members use CMarket's Cloudinary account as unrestricted storage.

**Independent Test**: Attempt to request upload authorization and associate media as an unauthenticated caller, a non-member, and a non-owner, and confirm each attempt is rejected.

**Acceptance Scenarios**:

1. **Given** an unauthenticated caller, **When** upload authorization is requested, **Then** the request is rejected.
2. **Given** an authenticated account that is not a current member of the target community, **When** upload authorization is requested, **Then** the request is rejected.
3. **Given** an existing listing, **When** an account other than its owner attempts to upload, associate, reorder, choose a cover, or remove its photos, **Then** the operation is rejected.
4. **Given** an authorized caller, **When** upload authorization is generated, **Then** it is short-lived and limited to listing-image uploads.
5. **Given** any browser response, bundle, HTML output, database record, Docker image, or log, **When** inspected, **Then** the Cloudinary API secret is absent.
6. **Given** an authorized upload authorization response, **When** the browser receives it, **Then** it may legitimately contain the Cloudinary upload endpoint (including cloud name or a complete upload URL), API key, timestamp, signature, and server-generated public ID, because the signed upload protocol requires them — and this is the only browser-reachable response permitted to carry Cloudinary-identifying values.
7. **Given** the uploader has received Cloudinary's own upload response, **When** it processes that response, **Then** it may hold the returned asset metadata temporarily in memory until the server verifies and associates the asset, and MUST NOT persist or display it as a delivery source.
8. **Given** a Cloudinary identifier supplied by the client, **When** the server attempts to associate it with a listing, **Then** the server verifies that the asset belongs to an authorized upload flow for that account.
9. **Given** a manipulated request referencing an unrelated Cloudinary asset, **When** it is processed, **Then** no listing-photo association is created.
10. **Given** a MASTER platform-operator identity, **When** listing-media upload authorization is requested, **Then** it is rejected, because a MASTER is never a marketplace participant.

---

### User Story 6 - Edit and delete Cloudinary listing media (Priority: P2)

A listing owner can add, remove, reorder, and replace Cloudinary-backed photos after publication. Unused assets are cleaned up from Cloudinary.

**Why this priority**: Listing media changes over time, and removed assets should not consume storage indefinitely.

**Independent Test**: Edit a listing, remove one image, upload a replacement, change the cover, and confirm the final listing media and Cloudinary assets match the saved state.

**Acceptance Scenarios**:

1. **Given** an existing listing with several Cloudinary photos, **When** its owner removes one and saves, **Then** that photo no longer appears on any CMarket surface and its image route no longer returns bytes.
2. **Given** a removed photo, **When** cleanup succeeds, **Then** its Cloudinary asset is deleted.
3. **Given** a temporary Cloudinary deletion failure, **When** the listing update completes, **Then** the failure is recorded for retry rather than silently ignored.
4. **Given** a listing is deleted, **When** deletion completes, **Then** all Cloudinary assets owned exclusively by that listing are deleted or placed into the retryable cleanup process.
5. **Given** an asset belongs to another listing or account, **When** a deletion request references it, **Then** the request is rejected.
6. **Given** the cover image changes, **When** any listing surface is opened, **Then** the new cover is used consistently.
7. **Given** an authorized upload that was never associated with any listing, **When** cleanup runs, **Then** that abandoned asset is identifiable and removable.

---

### User Story 7 - Replace the previous image system completely (Priority: P1)

After the feature is activated, every listing-image operation uses the single Cloudinary-backed system. The previous image-storage implementation is removed rather than preserved.

**Why this priority**: Maintaining two image systems would increase complexity and create inconsistent upload, rendering, and deletion behavior.

**Independent Test**: Inspect the finished schema and runtime code and confirm all listing-image uploads, reads, ordering, cover selection, rendering, and deletion use Cloudinary-backed photo records only.

**Acceptance Scenarios**:

1. **Given** the new feature is deployed, **When** a new listing image is uploaded, **Then** the file is stored in Cloudinary and not in PostgreSQL or the application container filesystem.
2. **Given** an existing listing containing only legacy image data, **When** the feature is deployed, **Then** the listing may become image-less and uses the existing no-photo placeholder.
3. **Given** the previous image fields, entities, upload routes, read paths, or rendering code are no longer needed, **When** the implementation is completed, **Then** they are removed.
4. **Given** the database schema must change, **When** the feature is deployed, **Then** an explicit Prisma migration applies the new schema.
5. **Given** runtime listing-media code, **When** inspected, **Then** it does not perform fallback reads from the previous image-storage implementation.
6. **Given** the finished application, **When** listing media is created, read, reordered, covered, or deleted, **Then** exactly one Cloudinary-backed implementation handles the operation.
7. **Given** the previous byte-serving read endpoint, **When** the feature is complete, **Then** it no longer reads from PostgreSQL and no surface references its old path.

### Edge Cases

- A member selects the same file more than once in the same pending batch.
- One image is corrupt despite having a supported filename extension.
- One image exceeds 10 MB.
- More than eight images are selected after combining existing and new photos.
- Uploads complete in a different order from the chosen display order.
- The browser tab closes after Cloudinary receives an upload but before the listing is saved.
- The database save fails after Cloudinary has already received one or more uploads.
- Cloudinary is temporarily unavailable, or returns a rate-limit or quota error — during upload, and separately during a delivery fetch.
- A signed upload authorization expires before a queued file begins.
- The current cover is removed while another image is still uploading.
- A portrait, landscape, extremely wide, or extremely tall image is uploaded.
- A very long or sensitive original filename is selected.
- A listing is deleted while media cleanup is temporarily failing.
- The user attempts to associate or delete an asset belonging to another account.
- A legacy listing no longer has a valid image after the hard cutover and must render the placeholder.
- A repeated listing-form submission attempts to save the same successful upload response twice.
- An existing listing that held more photos than the new ceiling under the previous system is edited after the cutover.
- A member loses community membership between requesting upload authorization and associating the asset.
- A member loses community membership, or the community is archived, while an already-loaded page still holds image route URLs.
- A photo is deleted while a browser still holds it in its private cache and issues a conditional request for it.
- Two accounts sign in sequentially in the same browser, and the second sends a conditional request for an image the first was authorized to see.
- An image route is requested with a well-formed but nonexistent photo identifier.
- An image route is requested with a variant name that does not exist.

## Requirements *(mandatory)*

### Functional Requirements

#### Custom uploader

- **FR-001**: CMarket MUST provide a custom listing-photo uploader inside the existing create-listing and edit-listing interfaces.
- **FR-002**: The integration MUST NOT use, display, embed, or load the Cloudinary Upload Widget.
- **FR-003**: Members MUST be able to select multiple image files in one file-selection action.
- **FR-004**: A listing MUST support at most eight associated photos, replacing the previous six-photo ceiling.
- **FR-005**: The uploader MUST accept JPEG, PNG, and WebP input and MUST reject every other type.
- **FR-006**: Each selected file MUST be 10 MB or smaller before upload.
- **FR-007**: Every selected file MUST show a preview and an individual upload state.
- **FR-008**: A selected image MUST be removable before the listing is saved.
- **FR-009**: An individual failed upload MUST be retryable without restarting successful uploads.
- **FR-010**: The uploader MUST remain usable at common desktop and mobile viewport widths, and MUST NOT depend on an interaction that touch input cannot perform.
- **FR-011**: The uploader MUST use bounded concurrency, with three simultaneous uploads as the default.
- **FR-012**: The listing form MUST NOT finish while any selected image remains in a waiting or uploading state.
- **FR-013**: Per-file rejection and failure messages MUST identify which file failed and why.

#### Ordering and cover

- **FR-014**: Members MUST be able to control listing-photo order.
- **FR-015**: Members MUST be able to select exactly one cover image when photos exist.
- **FR-016**: When no cover is explicitly selected, the first photo in display order MUST become the cover.
- **FR-017**: Upload-completion order MUST NOT replace the user's chosen display order.
- **FR-018**: Removing the cover MUST select a deterministic replacement when other photos remain.
- **FR-019**: Saving the same uploaded asset more than once MUST NOT create duplicate photo associations.
- **FR-020**: Display order MUST remain contiguous and unambiguous after any add, remove, or reorder operation.

#### Cloudinary upload architecture (unchanged by the delivery revision)

- **FR-021**: Image bytes MUST upload directly from the browser to Cloudinary.
- **FR-022**: Direct uploads MUST use short-lived signed parameters generated by CMarket.
- **FR-023**: Unsigned public upload presets MUST NOT be used for listing images.
- **FR-024**: `CLOUDINARY_API_SECRET` MUST remain exclusively on the server.
- **FR-025**: The Cloudinary API secret MUST never be returned to the browser.
- **FR-026**: Upload authorization MUST require an authenticated account.
- **FR-027**: Upload authorization MUST validate current community membership.
- **FR-028**: When editing an existing listing, upload authorization and media mutations MUST validate listing ownership.
- **FR-029**: Upload parameters MUST restrict assets to listing-media use and the current deployment environment.
- **FR-030**: CMarket MUST verify that an uploaded asset belongs to an authorized upload flow before associating it with a listing.
- **FR-031**: Arbitrary client-supplied Cloudinary asset identifiers MUST NOT be trusted without server verification.
- **FR-032**: Upload authorization and media mutations MUST NOT be available to a MASTER platform-operator identity.
- **FR-033**: Cloudinary-side upload constraints MUST enforce the accepted formats and the maximum file size, so a bypassed client cannot store a disallowed asset.

#### Cloudinary-backed database model

- **FR-034**: PostgreSQL MUST store listing-media references and presentation metadata, not image bytes.
- **FR-035**: The Cloudinary-backed listing-photo model MUST store a stable Cloudinary asset identifier.
- **FR-036**: The model MUST store the Cloudinary public ID.
- **FR-037**: The model MUST store the related listing ID.
- **FR-038**: The model MUST store image width and height.
- **FR-039**: The model MUST store the image format.
- **FR-040**: The model MUST store display order.
- **FR-041**: The model MUST store cover-image state or support deriving the cover deterministically from order.
- **FR-042**: The model MUST store creation timestamps.
- **FR-043**: The model MAY store Cloudinary version, asset byte size, or resource type when useful.
- **FR-044**: A stored URL MUST NOT be the only stable reference to the asset, and MUST NOT be the mechanism by which delivery resolves an asset.
- **FR-045**: PostgreSQL MUST NOT store image bytes, binary blobs, or base64 image values.
- **FR-046**: The application container filesystem MUST NOT be used as durable image storage.
- **FR-047**: The same Cloudinary asset MUST NOT be associable with more than one listing.
- **FR-048**: Deleting a listing MUST remove its photo records.

A compatible target model may contain:

- `id`
- `listingId`
- `cloudinaryAssetId`
- `cloudinaryPublicId`
- `width`
- `height`
- `format`
- `bytes`
- `displayOrder`
- `createdAt`

The implementation plan may adjust exact field names to match current project conventions, and may keep cover state on the listing rather than on the photo, provided exactly one cover is representable.

#### Authenticated image delivery

- **FR-049**: The browser MUST request every listing image from a CMarket route, never from Cloudinary.
- **FR-050**: The image route MUST be community-scoped and photo-addressed, of the form `/api/communities/{communityId}/listing-photos/{photoId}`.
- **FR-051**: Every image request MUST validate the signed-in session.
- **FR-052**: Every image request MUST validate the caller's current membership in the requested community.
- **FR-053**: Every image request MUST verify that the requested photo belongs to a listing in the requested community.
- **FR-054**: An invalid or unauthorized image request MUST be refused with the project's existing isolation behavior — a membership failure and a wrong-community or nonexistent photo MUST be indistinguishable from the caller's perspective in the way existing listing reads already are.
- **FR-055**: The image route MUST fetch the image from Cloudinary server-side and return the bytes to the browser.
- **FR-056**: No Cloudinary delivery URL, authenticated source URL, or persisted Cloudinary identifier MUST be exposed through listing reads or image-delivery responses — meaning listing pages, listing cards, galleries, listing service responses, association responses, and proxy responses, in body, header, HTML output, or client bundle. Cloudinary upload endpoints and temporary signed-upload metadata MAY be visible only during an authorized direct-upload flow, as specified in FR-108.
- **FR-057**: Cloudinary assets MUST NOT rely on publicly accessible delivery as the browser-facing access mechanism. Knowledge of an image route URL alone MUST NOT grant access without a valid current session and membership.
- **FR-058**: Image responses MUST use `Cache-Control: private, no-cache` with `ETag` support, so a browser may store the bytes but MUST revalidate with the server before reusing them. A time-based `max-age` that permits reuse without revalidation MUST NOT be used, and responses MUST NOT be cacheable by any shared or public cache. A stricter `private, no-store` mode MAY remain available as optional configuration, but `private, no-cache` with `ETag` is the selected MVP behavior.
- **FR-059**: Delivery MUST support a fixed set of server-defined image variants — at minimum thumbnail, card, and detail.
- **FR-060**: Variant selection MUST come from a server-side allowlist. Arbitrary client-supplied widths, dimensions, or transformation strings MUST NOT be honoured or forwarded to the storage provider.
- **FR-061**: An unrecognized variant name MUST be rejected or resolved to a safe server-defined default, never passed through.
- **FR-062**: An internal server-side byte cache is OPTIONAL and outside MVP scope. If added, it MUST perform full authorization before returning cached bytes.

#### Image presentation

- **FR-063**: Listing images MAY be rendered with a plain HTML `<img>` element or a small reusable CMarket image component. `next/image`, a Next.js image loader, `remotePatterns`, and `srcset` MUST NOT be required by this feature.
- **FR-064**: Images MUST preserve their natural aspect ratio without distortion.
- **FR-065**: Images MUST NOT cause horizontal overflow at any supported viewport width.
- **FR-066**: Images MUST use meaningful alternative text based on listing context, never a filename or internal identifier.
- **FR-067**: Non-cover gallery images MUST be lazily loaded.
- **FR-068**: Stored width and height MUST be used where useful to reserve space and reduce layout movement.
- **FR-069**: Existing no-photo placeholder behavior MUST remain supported, including its current test affordances.
- **FR-070**: Each rendering surface MUST request the variant appropriate to its display size rather than always requesting full-size bytes.

#### Listing integration

- **FR-071**: Cloudinary media MUST render on every surface that displays listing media, which at minimum means the three surfaces that display it today: the community main view, the community listings (discovery) view, and the listing detail gallery.
- **FR-072**: The scope of listing-media rendering is **replacement only**: this feature MUST NOT add listing thumbnails to Account, My listings, public profiles, or transaction listing context, none of which display listing media today. Adding them is captured as backlog work per Principle VII (Simplicity & MVP-First).
- **FR-073**: Both FOR_SALE and WANTED listings MUST render their media through the same Cloudinary-backed path.
- **FR-074**: Existing listing ownership, membership, community isolation, listing kind, status, stock, pricing, and editing rules MUST remain unchanged.
- **FR-075**: Listing-media association, ordering, cover selection, and removal MUST be server-authorized.
- **FR-076**: A failed upload MUST be retried or removed before listing submission can complete.
- **FR-077**: Image upload failures MUST NOT silently discard already successful uploads.

#### Deletion and cleanup

- **FR-078**: Removing a photo association MUST remove it from every CMarket listing surface, and its image route MUST stop returning bytes.
- **FR-079**: Assets no longer associated with a listing MUST be deleted from Cloudinary or entered into a reliable retryable cleanup process.
- **FR-080**: Deleting a listing MUST clean up every Cloudinary asset owned exclusively by that listing.
- **FR-081**: Cloudinary deletion MUST use stored stable asset references.
- **FR-082**: Temporary deletion failures MUST be recorded and retryable.
- **FR-083**: Unassociated uploads from abandoned or failed listing flows MUST be identifiable for cleanup.
- **FR-084**: An account MUST NOT delete or modify an asset belonging to another listing or account.
- **FR-085**: A Cloudinary cleanup failure MUST NOT block or roll back the listing operation that triggered it.

#### Hard cutover from previous image implementation

- **FR-086**: Cloudinary MUST become the only durable listing-image storage provider.
- **FR-087**: The feature MUST NOT migrate legacy image data to Cloudinary.
- **FR-088**: The feature MUST NOT preserve backward-compatible reads from the previous image-storage implementation.
- **FR-089**: Existing listings containing only legacy image data MAY become image-less and MUST use the no-photo placeholder.
- **FR-090**: Obsolete image fields, entities, routes, services, rendering branches, local-storage paths, blob fields, and base64 fields MUST be removed when no longer required.
- **FR-091**: The finished runtime MUST NOT contain two parallel listing-image implementations.
- **FR-092**: Every new upload, read, ordering change, cover selection, rendering operation, and deletion MUST use the Cloudinary-backed implementation.
- **FR-093**: A destructive Prisma schema migration is acceptable, and MUST discard legacy image bytes rather than retain an unused column.
- **FR-094**: Database changes MUST be applied through an explicit, versioned Prisma migration.
- **FR-095**: Production deployment MUST NOT depend on `prisma db push --accept-data-loss` to apply this feature.
- **FR-096**: Automated tests and fixtures that depend on the previous image implementation MUST be updated to the Cloudinary-backed model, without leaving a legacy code path alive solely to satisfy a test.

#### Privacy and operational safety

- **FR-097**: Cloudinary credentials MUST come from server-side environment configuration.
- **FR-098**: `CLOUDINARY_API_SECRET` MUST NOT use a `NEXT_PUBLIC_` environment variable.
- **FR-099**: No Cloudinary credential or cloud name MUST be required in the client bundle. `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` MUST NOT exist: the upload authorization response supplies the complete upload endpoint dynamically at runtime, and delivery needs no client-side Cloudinary value at all.
- **FR-100**: The API secret MUST NOT be stored in PostgreSQL, committed to Git, embedded in a Docker image, or logged.
- **FR-101**: Original filenames MUST NOT be displayed publicly or treated as trusted identifiers.
- **FR-102**: Asset naming and folder organization MUST avoid collisions across deployment environments, accounts, communities, and listings.
- **FR-103**: Non-production environments MUST NOT be able to delete or overwrite production assets.
- **FR-104**: Upload, delivery, and deletion failures MUST create actionable logs without exposing credentials or signed URLs.
- **FR-105**: Existing community-isolation and current-membership authorization rules MUST be preserved.
- **FR-106**: Missing or misconfigured Cloudinary configuration MUST fail loudly at first use rather than degrading silently into an image-less application.

#### Added by the 2026-08-06 amendment

Appended rather than inserted, so existing requirement numbers and every cross-reference to them stay stable — the convention `prisma/schema.prisma` already uses for the 2026-07-17 cover-photo amendment.

- **FR-107**: The authenticated image proxy MUST fetch and stream the image bytes itself. It MUST NOT redirect, rewrite, or otherwise hand the browser a Cloudinary URL to follow, because a redirect would place the signed source URL in the browser's network log, history, and referrer — defeating FR-056 while appearing to satisfy it.
- **FR-108**: During an authorized direct upload, the browser MAY receive the Cloudinary upload endpoint (cloud name or a complete upload URL), API key, timestamp, signature, and the server-generated public ID, because the signed upload protocol requires them. The uploader MAY also process Cloudinary's upload response temporarily in memory before the server verifies and associates the asset. This exposure is bounded to the upload flow: it MUST NOT be persisted to storage the browser can re-read, rendered, logged client-side, or used as a delivery source. `CLOUDINARY_API_SECRET` is excluded from this allowance without exception, per FR-024, FR-025, FR-098, and FR-100.
- **FR-109**: The image proxy MUST complete session, current-membership, and photo-to-community validation **before** returning either `200` with bytes or `304 Not Modified`. A conditional request MUST NOT short-circuit authorization: an `ETag` match alone MUST NOT produce a `304`.

### Key Entities *(include if feature involves data)*

- **Listing** *(existing)*: Owns zero to eight ordered Cloudinary-backed photos. Its non-media business rules — ownership, community, kind, status, stock, price — remain unchanged.
- **ListingPhoto** *(evolved; bytes removed)*: Associates one listing with one Cloudinary asset and stores stable Cloudinary references, dimensions, format, display order, and creation timestamp. It no longer holds image data.
- **Cloudinary Asset** *(external)*: The actual remotely stored image resource, addressed by a stable identifier rather than by URL, and reachable only by the CMarket server.
- **Upload Authorization** *(temporary, derived)*: Short-lived signed parameters generated for an authenticated, authorized upload, scoped to listing-media use and the current environment. Not a permanent marketplace entity.
- **Pending Upload** *(temporary; persistence decided during planning)*: Identifies an authorized uploaded asset before final listing association, enabling ownership verification and abandoned-upload cleanup.
- **Media Cleanup Task** *(new, operational)*: A durable record of an asset that must be removed from Cloudinary, retried until it succeeds, so a transient provider failure never silently orphans storage.
- **Image Variant** *(derived, server-defined)*: A named, fixed rendition — thumbnail, card, detail — mapping to a server-controlled transformation. The client selects a name, never dimensions.
- **Listing Media View** *(derived)*: The ordered media representation consumed by listing surfaces, exposing the cover and the ordered gallery with dimensions and alternative text, and referencing images by CMarket route rather than by provider URL.
- **Legacy Listing Image Data** *(removed)*: The previous in-database byte representation. Not migrated, not preserved.

## Assumptions

- Cloudinary is the only durable listing-image storage provider after this feature is activated. It is not the browser-facing delivery mechanism.
- CMarket does not use the Cloudinary Upload Widget.
- Upload stays a direct, signed, browser-to-Cloudinary transfer. Only delivery is proxied — the two directions are deliberately asymmetric, because upload bytes are large and one-time while delivery bytes are the thing that must stay access-controlled.
- The previous image-storage method is intentionally discarded; legacy images are not migrated, and existing listings may lose their images and fall back to the no-photo placeholder.
- Prisma schema changes and destructive migration operations are acceptable, but the change must still reach production through an explicit versioned Prisma migration, per the constitution's migrations constraint.
- PostgreSQL stores only Cloudinary references and listing presentation metadata, never image bytes.
- The create-listing and edit-listing flows can host a custom client-side uploader; both flows share one uploader component.
- The per-listing photo ceiling rises from six to eight. Existing listings already at or above the old ceiling are not rewritten; the new ceiling applies to subsequent edits.
- Accepted source formats are JPEG, PNG, and WebP; maximum source file size is 10 MB per image; default upload concurrency is three files at a time.
- The Cloudinary cloud name and API key may be returned to authorized clients where the upload protocol requires it; the API secret never leaves the server. Delivery needs no client-side Cloudinary configuration at all, so no `NEXT_PUBLIC_CLOUDINARY_*` variable exists.
- Upload exposure and delivery exposure are different problems with different answers. Upload is a one-time, signature-authorized transfer that structurally requires the browser to know where to send bytes. Delivery is a repeated read of content whose access must be re-checked. Treating them identically would either break the upload protocol or leak a durable delivery capability; the spec therefore constrains them separately (FR-056, FR-108).
- Image delivery accepts that the application server is on the byte path. This is a deliberate trade of bandwidth and latency for preserved membership gating, mitigated by predefined variants and conditional-request revalidation rather than by relaxing access control.
- Every cached image reuse costs one conditional request. This is accepted as the price of correct revocation: `no-cache` means a browser still stores the bytes and a `304` is cheap, but authorization is re-run every time, so leaving a community or switching accounts takes effect on the very next image request rather than after a TTL.
- Predefined variants are sufficient; no surface needs an arbitrary size, and responsive art direction is out of scope.
- Cloudinary transformations produce variants on demand rather than storing separate physical files per display size.
- `next/image` is optional. A plain `<img>` is acceptable, and the lint rule discouraging raw image elements may be suppressed in the single shared media component with a comment explaining why.
- Listing media is not subject to moderation, approval, or content scanning in this feature.
- Videos, GIF-specific features, PDFs, avatars, profile photos, chat attachments, transaction attachments, image comments, AI-generated images, moderation, interactive cropping, notifications, and the Cloudinary Upload Widget are out of scope.

## Dependencies

- A Cloudinary account with a cloud name, API key, and API secret provisioned per deployment environment, injected as server-side environment configuration.
- Outbound network access from the application server to Cloudinary, for uploads' verification step, for delivery fetches, and for deletion. Delivery now depends on this at request time, not only at write time.
- Existing authentication, membership, and listing-authorization behavior, reused unchanged for upload authorization, media mutation checks, and the delivery route's own gate.
- The existing create-listing and edit-listing forms, which host the new uploader.
- The deployment pipeline's ability to apply a versioned Prisma migration.

## Constitution Alignment

Noted here because the plan's Constitution Check depends on it:

- **Principle II (Community Isolation, NON-NEGOTIABLE)** is **preserved, not relaxed.** The authenticated proxy re-applies session and current-membership validation on every single image request — including conditional requests, before any `304` (FR-109) — exactly as the current byte endpoint does, and additionally verifies the photo's listing belongs to the community named in the path. No Cloudinary delivery URL ever reaches a browser and the proxy never redirects to one (FR-107), so there is no bearer capability that outlives membership. With `no-cache` there is no TTL window either: revocation takes effect on the next request. This is the reason the earlier revision's maintainer sign-off requirement is gone.
- **Principle V (Single web app, PWA)** requires the uploader and every media surface to be fully usable in a mobile viewport — hence FR-010, FR-065, and SC-014, including touch-reachable reordering.
- **Principle VI (Contact & Data Privacy Gating)** is strengthened: random asset identifiers mean a member's original filename never appears in any URL or markup, and the proxy means asset locations are not browser-visible at all.
- **Principle VII (Simplicity & MVP-First)** is why rendering scope stays at the three surfaces that show media today, why the optional server-side byte cache is explicitly excluded from MVP (FR-062), and why no image-rendering library is introduced.
- **Principle VIII (Test Discipline)** names product listing as a critical flow, so listing-media behavior changes — including the delivery route's authorization matrix — must be covered by tests that run in CI and block merge.
- **Migrations constraint** forbids reaching production by anything other than a versioned Prisma migration — see FR-094 and FR-095.
