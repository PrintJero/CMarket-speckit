# Feature Specification: Accounts and Authentication

**Feature Branch**: `002-accounts-authentication`

**Created**: 2026-07-15

**Status**: Draft

**Input**: User description: "Accounts and authentication in CMarket. Anyone may create a CMarket account on their own, without a prior invitation, using email and password or federated identity with Google. A newly created account belongs to no community, and in that state it can see and do nothing at all: no listings, no members, no activity, and it cannot discover or enumerate which communities exist. An account with no memberships is a valid, permanent state. Sign up with email and password. Sign up and sign in with Google. Mandatory email verification for accounts created with email and password; an unverified account may exist and sign in but MUST NOT accept any community invitation; Google accounts inherit verification from the provider. Sign in, sign out, and persistent session. Sign-up attempts against an already-registered email MUST NOT reveal that the account exists. Passwords are never stored or compared in plaintext, and no alternative authentication path bypasses verification against the stored password. Out of scope: profiles/avatars, password recovery, two-factor authentication, global platform roles, account deletion, and anything related to communities, invitations, or memberships."

## Clarifications

### Session 2026-07-15

- Q: What minimum password policy should apply to email/password signup? → A: Minimum 8 characters, checked against a common/breached-password blocklist (no forced mix of character types)
- Q: When comparing emails to detect duplicates (FR-009) or to auto-link a Google identity to an existing password account (FR-015), how should two email addresses be considered "the same"? → A: Case-insensitive exact match (lowercase the whole address before comparing; no provider-specific canonicalization such as ignoring Gmail dots or +tags)

### Session 2026-07-16 (security amendment)

- Q: FR-015 originally auto-linked Google to a pre-existing email/password account "verified or not," preserving the password credential either way. This enables pre-hijacking: an attacker registers `victim@x.com` with a password, never verifies it, and waits for the real owner to sign in with Google — after which the attacker's untouched password still authenticates into the now-verified, victim-owned account. → A: Split the behavior by the pre-existing account's verification state. If already verified: link and preserve the password credential (unchanged). If NOT verified: link, mark verified, but discard the password credential (an unverified credential is untrusted the moment a different channel proves ownership), revoke all existing sessions for that account, and invalidate any pending verification tokens. Memberships and history are preserved either way; rejecting the link outright was considered and rejected, since it would let an attacker permanently lock the real owner out by squatting their email.

### Session 2026-07-16 (security amendment #2)

- Q: The FR-018 fix above discards an unverified account's password credential only when Google later links to it — but the same untrusted-credential problem exists purely within the email/password flow itself: an attacker registers `victim@x.com` with their own password and never verifies it; later the real owner submits their own sign-up with their own password; the system re-sends a verification email (to the real owner's inbox) but silently discards the real owner's submitted password; when the real owner clicks their own verification link, the account becomes verified — with the attacker's original password still attached. The real owner's own click is the exploit step. → A: A password credential MUST NOT be attached to an Account before its email is verified at all — not only in the Google-auto-link case. The candidate password from an email/password sign-up attempt is stored on the issued VerificationToken, not on the Account; consuming a token applies that token's candidate credential to the Account only if the Account is still unverified at that moment (never overwrites an already-verified Account's credential); each repeated sign-up attempt against an unverified Account issues its own token with its own candidate credential, and — unchanged from FR-014 — issuing a new token invalidates whichever token preceded it, so only the most recently submitted attempt's password can ever end up attached. Direct consequence, addressed explicitly: an Account with no credential attached yet (i.e., not yet verified, and never linked to Google) cannot sign in with a password at all, since none exists to check against — this replaces the earlier, now-inaccurate assumption that an unverified account can sign in.

### Session 2026-07-16 (security amendment #3)

- Q: Amendment #2's own fix introduced a new problem: because a repeated sign-up invalidates the prior pending token, "whichever sign-up call happens last wins" — an attacker can call sign-up repeatedly for `victim@x.com` purely to destroy the real owner's live token and replace it with one carrying the attacker's own candidate password. Both verification emails land in the same (victim's) inbox; whichever link the victim clicks, if it's not literally the very first one they received, is now the attacker's. This is not irreducible — it exists only because a competing sign-up destroys the legitimate token rather than merely adding another one. → A: Sign-up against an existing unverified account MUST NOT invalidate previously issued tokens; multiple pending tokens MAY coexist, each carrying its own candidate credential. FR-020's existing "first consumption while unverified wins, and applies that consumption's own candidate" already resolves the race correctly without needing to destroy anyone's token — whichever token the real owner consumes first (in particular, their own, if they act on it) is the one that takes effect, and every other still-pending token for that account becomes invalid the moment that happens. `resendVerification` MAY continue to invalidate prior tokens, since it re-issues the same candidate credential rather than introducing a competing one. Acknowledged, not fixed by this amendment: an attacker who consumes a token *before* the real owner does still wins that particular race (this is a phishing/timing risk inherent to any first-click-wins email-link scheme, not a defect this amendment introduces or claims to remove) — what this amendment removes is the *destructive* half of the old defect, where a competing sign-up could invalidate the legitimate holder's own link out from under them. Separately: unthrottled repeated sign-up/resend for the same email is the amplifier that makes the (now-fixed) destructive attack cheap to attempt at all repeatedly; per-email rate limiting on sign-up and resend-verification is added (FR-021), correcting the prior Assumption that this was out of scope.
- Q: Consuming a verification token whose candidate credential is null (no password was ever collected for it) currently still marks the account verified, leaving `passwordHash` null — with no password-recovery flow in scope, that account becomes permanently unusable. Today this is reachable only for an unverified `Account` created outside `signUp()` (bypassing the normal flow, as some tests do directly); a future community-bootstrap spec is expected to create `Account` rows directly, making this reachable for real. → A: Consuming a verification token whose candidate credential is null MUST NOT verify an account that has no password credential of its own already — that would create a dead end. The verification attempt fails explicitly instead (FR-022); the token is still consumed (it cannot be retried to a different outcome, since its stored candidate never changes).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Create an account with email and password, gated by verification (Priority: P1)

A visitor with no prior invitation creates a CMarket account using their own email address and a password. The account exists immediately, but no password credential is attached to it — and it cannot accept any community invitation — until the visitor confirms ownership of the email address by following the verification link, at which point their submitted password becomes the account's credential and it can be signed into.

**Why this priority**: This is the primary, self-serve entry point into CMarket and the one place where the constitutional rule "membership must originate from an administrator, but identity must be self-created and verified" is enforced end to end. Every other flow in this spec builds on the existence of a global, verified-or-not account.

**Independent Test**: Can be fully tested by signing up with a fresh email and password, confirming the account exists in an unverified state, confirming an attempt to accept a community invitation is rejected, then verifying the email and confirming invitation acceptance is now permitted.

**Acceptance Scenarios**:

1. **Given** no account exists for a given email, **When** a visitor submits sign-up with that email and a password, **Then** an account is created in an unverified state (no password credential attached yet) and a verification email is sent.
2. **Given** an unverified email/password account, **When** the account holder attempts to accept a community invitation, **Then** the system blocks the acceptance and explains that email verification is required first.
3. **Given** an unverified email/password account, **When** the account holder follows the verification link sent to their email, **Then** the account becomes verified, that submission's password becomes the account's credential, and the account can subsequently be signed into and accept a community invitation.
4. **Given** an account (verified or not) already exists for an email, **When** a new sign-up is submitted for that same email, **Then** the system responds the same way it would to a brand-new sign-up, without revealing that an account already exists.
5. **Given** an unverified account, **When** more than one sign-up attempt is submitted for that same email — whether the same person retrying or a different party entirely — **Then** each attempt receives its own independent, pending verification token carrying its own candidate password; no earlier attempt's token is invalidated or destroyed by a later one.
6. **Given** an unverified account with more than one pending verification token from different sign-up attempts, **When** the account holder follows the verification link from their own original sign-up, **Then** their own password becomes the account's credential regardless of how many other sign-up attempts were submitted afterward for that same email, the account becomes verified, and every other pending token for that account becomes invalid at that same moment.
7. **Given** the sign-up form, **When** a visitor enters a password and a different confirmation value, **Then** the form shows an inline error and does not submit — no request reaches the server (FR-023).
8. **Given** the post-sign-up "Check your email" screen, **When** the visitor selects "Resend verification email" or "Back to sign in," **Then** the resend action shows the identical, generic acknowledgement regardless of the email's actual state (FR-024), and the sign-in link navigates away from the otherwise dead-end screen.

### User Story 2 - Sign in, sign out, and stay signed in (Priority: P1)

An existing account holder signs in with their credentials, remains signed in across app restarts without re-entering credentials, and can explicitly sign out to end that session.

**Why this priority**: Without reliable sign-in/out and session persistence, an account is unusable day-to-day; this is as foundational as account creation itself.

**Independent Test**: Can be fully tested by signing in with valid credentials, restarting the app/browser and confirming the session is still active, then signing out and confirming the session no longer grants access.

**Acceptance Scenarios**:

1. **Given** an existing account with a password credential attached (i.e., verified), **When** the holder signs in with the correct password, **Then** a session is established that persists across app restarts until sign-out or natural expiry.
2. **Given** an existing, verified account, **When** sign-in is attempted with an incorrect password, **Then** the system rejects it with a generic invalid-credentials message that does not reveal whether the email is registered.
3. **Given** an active session, **When** the account holder signs out, **Then** the session is invalidated and no longer grants access on that device.
4. **Given** an account that has not yet been verified (no password credential attached to it yet), **When** anyone attempts to sign in to it with any password, **Then** the system rejects it with the same generic invalid-credentials message used for any other failed sign-in — there is no credential yet to match, and this is indistinguishable from a wrong password on a verified account.

---

### User Story 3 - Sign up or sign in with Google (Priority: P2)

A visitor creates a CMarket account, or an existing account holder signs in, using their Google identity instead of an email/password. Because Google has already confirmed the email, the resulting account is treated as verified immediately.

**Why this priority**: Federated sign-in reduces friction for a large share of users and removes an entire class of password-related support issues, but the product is fully usable via email/password alone, so this ships after Stories 1 and 2.

**Independent Test**: Can be fully tested by completing Google sign-in for an email with no prior CMarket account, confirming a verified account is created with zero memberships, and confirming that account can accept a community invitation immediately without a separate verification step.

**Acceptance Scenarios**:

1. **Given** no CMarket account is linked to a given Google identity, **When** a visitor completes sign-up via Google, **Then** a new account is created, marked verified, with zero community memberships.
2. **Given** an account already linked to a Google identity, **When** the holder signs in via Google again, **Then** the existing account's session is established rather than a duplicate account being created.
3. **Given** a Google-created (verified) account, **When** the holder attempts to accept a community invitation, **Then** the acceptance is permitted without any additional email-verification step.
4. **Given** an existing, already-verified email/password account, **When** the same person completes Google sign-up using that same email, **Then** Google is linked as an additional sign-in method on that same account, its password credential is preserved unchanged, and its existing memberships and history are unchanged — no second account is created.
5. **Given** an existing, unverified email/password account, **When** someone completes Google sign-up using that same email, **Then** Google is linked and the account becomes verified, but its pre-existing password credential is discarded, every existing session for that account is revoked, and any pending verification token for it is invalidated — its memberships and history are preserved, and no second account is created.

---

### Edge Cases

- What happens when a visitor tries to sign up via Google using an email address that already has an email/password account under it? The system MUST auto-link Google as an additional sign-in method on that same existing account (trusting Google's own email verification as proof of ownership) rather than creating a second, disconnected account. If that existing account was already verified, its password credential is preserved unchanged. If it was NOT verified, marking it verified here MUST NOT let any credential submitted before this moment ever take effect: any pending verification token for that account (which is where an unconsumed candidate credential lives — see the sign-up edge case below) MUST be invalidated, and any session for that account MUST be revoked, in addition to marking the account verified. This closes a pre-hijacking window: an attacker who registers a victim's email with a password and never verifies it MUST NOT retain silent access once the real owner proves ownership via Google. Memberships and history are preserved in both cases; outright rejecting the link is not an option, since that would let the same attacker permanently lock the real owner out by squatting their email.
- What happens when someone submits sign-up for an email that already has an unverified account (e.g., someone else registered that email first, by mistake or maliciously, and never verified it)? The system MUST still respond as if a new account were created (per Story 1, scenario 4) and MUST send a verification email carrying this attempt's own candidate credential as a side effect, without ever confirming or denying prior existence — and, since security amendment #3, this new token MUST NOT invalidate or destroy any other still-pending token for that account (Story 1, scenario 5): an earlier registrant's pending token, and the legitimate holder's own pending token, are equally undisturbed by it. Only the candidate credential belonging to whichever pending token is later actually consumed first ever gets attached to the account (FR-020) — and the moment that happens, every other pending token for that account becomes invalid (Story 1, scenario 6).
- What happens when a verification link has expired or was never received? The account holder MUST be able to request that a new verification email be sent (subject to the rate limit below); unlike a competing sign-up, this resend MAY invalidate whichever prior token(s) it replaces, since it carries forward the same candidate credential rather than introducing a competing one (FR-014).
- What happens when many sign-up or resend-verification requests arrive for the same email address in a short time? Beyond a specified threshold, the system MUST silently stop issuing new tokens or sending emails for that address until the window passes, while still returning the identical non-enumeration response as any other sign-up or resend request (FR-021) — this is the direct amplifier-control for the coexisting-tokens model above: without it, an attacker could still cheaply flood a victim's inbox with competing pending tokens, none of which can now destroy the victim's own, but all of which are still noise and still a race the victim could lose if they click the wrong one first.
- What happens when a verification token whose candidate credential is null (no password was ever collected for it) is consumed against an account that has no password credential of its own either? The system MUST NOT mark that account verified — doing so would create a permanently unusable, verified-but-passwordless account, since no password-recovery flow exists in this spec. The token is still consumed either way (FR-022).
- What happens when an unverified account simply never verifies? It remains a valid, permanent Account record (FR-004) that can never accept a community invitation and — since no password credential has ever been attached to it — cannot be signed into with a password either; no automatic deletion or downgrade occurs, and a fresh sign-up or resend request can still move it toward verification at any time (subject to the rate limit above).
- What happens when a signed-in user's session expires naturally (not via explicit sign-out)? The user is treated as signed out and must sign in again to regain access.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow any visitor to create a CMarket account using an email address and password, without any prior invitation or credential.
- **FR-002**: System MUST allow any visitor to create a CMarket account, or sign in to an existing one, using federated Google identity, without any prior invitation or credential.
- **FR-003**: A newly created account MUST start with zero community memberships, and in that state MUST NOT expose any listing, member roster, activity, or the ability to discover or enumerate which communities exist.
- **FR-004**: System MUST treat an account with zero community memberships as a valid, permanent state that requires no further action and never expires or degrades on its own.
- **FR-005**: System MUST require email verification for accounts created with email and password before such an account may accept a community invitation.
- **FR-006**: System MUST treat accounts created via Google sign-up as verified immediately, inheriting the provider's verification, permitting immediate community-invitation acceptance with no separate CMarket-side verification step.
- **FR-007**: An account that has not yet been verified — and therefore has no password credential attached to it yet (FR-019) — MUST NOT be able to sign in with a password, since none exists yet to check against; it MUST still support account-level functions that don't require being signed in, specifically requesting the verification email be re-sent (FR-014). Once verified — whether by consuming its verification token (FR-020) or by a Google auto-link (FR-006/FR-018) — it can be signed into like any account, but remains blocked from accepting any community invitation until that verification has occurred (FR-005).
- **FR-008**: System MUST allow an account holder to sign in and to explicitly sign out, and MUST keep a signed-in session persistent across application restarts until the holder signs out or the session naturally expires.
- **FR-009**: When sign-up is attempted for an email that already has an account (verified or unverified), the system MUST respond identically to how it responds to a brand-new sign-up, without revealing that the account already existed.
- **FR-010**: When sign-in is attempted with incorrect credentials, the system MUST respond with a generic invalid-credentials message that does not reveal whether the submitted email is registered.
- **FR-011**: System MUST store passwords only as the output of a one-way, industry-standard hashing function, and MUST NEVER store or compare a password in plaintext, under any circumstance.
- **FR-012**: System MUST NOT expose any authentication path — administrative override, support tooling, alternate endpoint, or otherwise — that signs a user into a password-based account without validating the submitted password against its stored hash.
- **FR-013**: System MUST prevent any account, regardless of verification status or sign-up method, from discovering, listing, or enumerating which communities exist while it holds no membership.
- **FR-014**: System MUST allow an account holder with an unverified email/password account to request that the verification email be re-sent (subject to FR-021's rate limit); the re-sent token MUST carry forward the same candidate credential as the token(s) it replaces, since no new password is collected on a resend. Unlike a competing sign-up (FR-019/FR-021's coexistence rule), a resend MAY invalidate prior pending token(s) for that account, since it re-issues the same credential rather than introducing a competing one.
- **FR-015**: When Google sign-up is completed for an email that already has an existing, **already-verified** email/password account, system MUST auto-link Google as an additional sign-in method on that same account (treating Google's own email verification as proof of ownership), preserve its password credential unchanged, and preserve its existing memberships and history unchanged — the system MUST NOT create a second, disconnected account for the same person.
- **FR-016**: System MUST reject an email/password sign-up whose password is fewer than 8 characters or matches a known common/breached-password list; no other composition rule (e.g., forced mix of character types) MUST be required.
- **FR-017**: System MUST compare email addresses using a case-insensitive exact match (the full address lowercased) when detecting an existing account (FR-009) or auto-linking a Google identity to an existing password account (FR-015, FR-018); no provider-specific canonicalization (e.g., ignoring Gmail dots or +tags) MUST be applied.
- **FR-018** *(mechanism revised 2026-07-16 — see FR-019/FR-020)*: When Google sign-up is completed for an email that already has an existing but **unverified** email/password account, system MUST auto-link Google as an additional sign-in method on that same account and mark it verified. Because FR-019 already guarantees an unverified account never carries a password credential, there is normally nothing to discard at that moment — but as defense-in-depth against that invariant ever being violated (e.g., by a defect, or by data predating this rule), the system MUST additionally ensure the account's password credential is empty, MUST invalidate any pending, unconsumed verification token for that account (the one remaining place an un-applied candidate credential can exist — FR-019), and MUST revoke every existing session for that account. Memberships and history MUST be preserved unchanged, and the system MUST NOT create a second, disconnected account for the same person. (Security rationale: a password credential established before any proof of email ownership is untrusted the moment ownership is proven through a different, trusted channel — Constitution Principle I's identity-binding guarantee would otherwise be defeated by an attacker who registers and never verifies a victim's email.)
- **FR-019** *(revised 2026-07-16 security amendment #3 — see amendment #2 for original)*: System MUST NOT attach a password credential to an Account before that Account's email has been verified. The candidate password hash from an email/password sign-up attempt MUST be stored on the VerificationToken issued for that attempt, never on the Account, until the token is consumed. Each sign-up attempt against an already-existing, unverified Account MUST issue its own independent token carrying its own candidate credential, and this issuance MUST NOT invalidate, consume, or otherwise disturb any other still-pending token for that Account — multiple pending tokens, each with their own candidate credential, MAY coexist for the same Account. (Contrast with `resendVerification`, FR-014, which MAY invalidate prior tokens, since it does not introduce a competing credential.)
- **FR-020** *(revised 2026-07-16 security amendment #3 — see amendment #2 for original)*: Consuming a verification token MUST apply that token's candidate password credential to its Account and mark the Account verified, but this MUST occur only if the Account is not already verified at the moment of consumption; if the Account is already verified (by any means), consuming the token MUST NOT modify the Account's password credential, though the token itself is still consumed (preventing replay) and the request is still treated as successful, since the account's email is indeed verified either way. The moment a token's consumption is what verifies the Account (i.e., it was not already verified), every other still-pending token for that same Account MUST also be invalidated — since FR-019 now allows multiple pending tokens to coexist, this is what makes each of the others concretely and observably dead rather than silently inert.
- **FR-021** *(new, 2026-07-16 security amendment #3)*: System MUST apply a per-email rate limit to verification-token issuance, shared across sign-up (FR-001/FR-019) and resend-verification (FR-014) requests against the same Account: beyond a specified number of tokens issued within a specified recent time window, further requests MUST NOT issue a new token or send an email, while still returning the identical response as any other request of that type (preserving FR-009's non-enumeration). This directly limits how cheaply an attacker can flood an account with competing pending tokens under FR-019's coexistence rule. (Supersedes the prior Assumption that rate-limiting was out of scope for this feature — see Assumptions.)
- **FR-022** *(new, 2026-07-16 security amendment #3)*: Consuming a verification token whose candidate credential is null MUST NOT verify an Account that has no password credential of its own already — doing so would mark the Account verified while leaving it permanently unable to be signed into with a password, since no password-recovery flow is in scope. The token MUST still be consumed (marked unusable) regardless of this outcome.
- **FR-023** *(new, 2026-07-16, client-side typo guard)*: The email/password sign-up form MUST require the password to be entered twice (a confirmation field) and MUST prevent submission when the two entries do not match, showing an inline error instead. This is a client-side typo guard only: it introduces no server-side requirement, MUST NOT change the sign-up API contract (FR-001), and MUST NOT add any field to the request body. (Rationale: password recovery is out of scope for this feature, so a typo in the password field — with no way to correct it afterward — would otherwise produce a permanently unusable account once the email is verified, since FR-020 applies whatever candidate credential the token carries.)
- **FR-024** *(new, 2026-07-16, post-sign-up screen wayfinding)*: The post-sign-up confirmation screen ("Check your email") MUST offer a "Resend verification email" action (wired to the existing resend-verification endpoint, FR-014) and a link back to sign-in, so the screen is never a dead end. The resend action MUST show the identical, generic acknowledgement regardless of whether the email has an account, is already verified, or is currently rate-limited (FR-009, FR-021) — presentation and wiring only; it MUST NOT change the resend-verification API contract or introduce any new server-side behavior.

### Key Entities

- **Account**: A person's single, global CMarket identity, independent of any community. Key attributes: email address (unique per account, compared case-insensitively), optional password credential (present only once verified — see Verification Token), linked federated identity (e.g., Google), verification status, creation timestamp. Exists and is meaningful with zero memberships.
- **Session**: A persistent, authenticated instance of an Account being signed in on a device, created at sign-in and ended by explicit sign-out or natural expiry.
- **Verification Token**: A single-use, time-limited proof-of-email-ownership token issued for one email/password sign-up attempt. Until consumed, it privately carries that attempt's candidate password so the credential is never attached to the Account before ownership of the email is proven (FR-019, FR-020). An Account MAY have more than one pending token at once, each from a different sign-up attempt — the first one consumed wins, and all others become invalid at that moment (FR-019, FR-020).
- **Community Membership** *(referenced, not owned by this spec)*: The link between an Account and a community, created only through the existing invitation flow. This spec defines the verification gate that membership acceptance depends on, not the membership flow itself.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A new visitor can complete email/password sign-up and reach the "check your email to verify" state in under 1 minute.
- **SC-002**: A new visitor can complete Google sign-up and reach a usable, verified account in under 30 seconds, with no additional verification steps.
- **SC-003**: 100% of unverified email/password accounts are prevented from accepting a community invitation until verification completes.
- **SC-004**: 100% of accounts with zero community memberships show zero listings, members, and activity, and cannot enumerate any community's existence.
- **SC-005**: Sign-up attempts against an email that already has an account are indistinguishable, in 100% of tested cases, from sign-up attempts against a brand-new email.
- **SC-006**: Returning account holders remain signed in across application restarts without needing to re-authenticate, until they explicitly sign out.
- **SC-007**: A security review confirms zero code paths store or compare a password in plaintext, and zero authentication paths bypass password validation.
- **SC-008**: 100% of Google auto-links against a previously unverified account result in that account's prior password credential no longer authenticating and all of its prior sessions being revoked, verified by test.
- **SC-009** *(revised 2026-07-16 security amendment #3)*: 100% of accounts targeted by more than one email/password sign-up attempt while unverified authenticate, after verification, only with the password belonging to whichever attempt's token is consumed first — regardless of submission order — verified by test.
- **SC-010**: 100% of an account's own pending sign-up token remains consumable and unaffected by any number of later, competing sign-up attempts submitted for that same email — verified by test.
- **SC-011**: Sign-up and resend-verification requests for the same email beyond the specified rate-limit threshold are indistinguishable, in 100% of tested cases, from requests within the threshold, while issuing no new token or email beyond it — verified by test.
- **SC-012**: 100% of verification-token consumptions with no candidate credential and no pre-existing account credential leave the account unverified rather than producing a permanently passwordless verified account — verified by test.

## Assumptions

- A verification email link expires after a standard, reasonable window and can be re-requested at any time by an unverified account holder; the exact expiry duration is an implementation detail.
- "Persistent session" means the account holder stays signed in across browser/app restarts for an extended period, consistent with standard session practices, until explicit sign-out or natural expiry; the exact session lifetime is an implementation detail.
- Signing out ends only the current session/device; signing out of all devices at once is not required by this spec.
- **Corrected 2026-07-16 (security amendment #3)**: rate-limiting sign-up and resend-verification per email is no longer treated as generic, out-of-scope hygiene — it is specified in FR-021, because unthrottled repetition there is a direct, feature-specific amplifier for the token-coexistence model (FR-019). Rate-limiting *other* endpoints not touched by this feature (e.g., sign-in attempts) remains expected as standard security hygiene, not separately specified here, since it is not unique to this feature.
- Standard security-event logging (sign-up, sign-in success/failure, verification, Google linking) is expected as baseline operational practice; specific log fields, retention, and tooling are implementation details left to planning.
- Google is the only federated identity provider in scope for this spec; other providers are out of scope.
- The community-invitation acceptance flow itself (validating tokens, creating pending memberships, administrator approval) is owned by the existing invitations feature; this spec only defines the account-verification gate that flow depends on.
- Per Constitution Principle VIII, account registration and sign-in/sign-out are critical flows: tests MUST be written first, MUST fail first, and implementation MUST proceed only to make them pass.
