# Research: Accounts and Authentication

**Input**: [spec.md](./spec.md) Technical Context unknowns
**Output**: Decisions below; no NEEDS CLARIFICATION remain for Phase 1.

## 1. Password hashing algorithm

- **Decision**: Argon2id, with bcrypt as the documented fallback only if the deployment runtime cannot run Argon2 natively.
- **Rationale**: OWASP's current password-storage guidance recommends Argon2id as the first choice; it is resistant to both GPU-cracking and side-channel attacks and has first-class Node.js library support. Satisfies FR-011/FR-012 (one-way hash, no plaintext path).
- **Alternatives considered**: bcrypt (older, still acceptable, weaker against GPU attacks at equal cost settings); scrypt (less common tooling/support in the Next.js ecosystem).

## 2. Session strategy

- **Decision**: Database-backed sessions (Prisma-persisted), not stateless JWT-only sessions.
- **Rationale**: Story 2 scenario 3 requires that signing out immediately invalidates the session ("no longer grants access on that device"). A pure stateless JWT cannot be revoked before its expiry without an additional blocklist, which is extra complexity for the same outcome a database session gives for free. A DB-backed session row can be deleted at sign-out and checked on each request.
- **Alternatives considered**: Stateless JWT (rejected: cannot satisfy immediate revocation without a denylist, which just re-introduces server-side state anyway — Principle VII favors the simpler path that doesn't need both).

**Addendum (discovered during implementation)**: NextAuth v4's `CredentialsProvider` always issues a stateless, JWT-encoded session cookie — it bypasses the adapter's `createSession` entirely even when `session.strategy: "database"` is configured for other providers. This cannot satisfy Story 2 scenario 3 (sign-out must immediately, server-side revoke access). Resolution: email/password sign-in and sign-out are implemented as our own routes (not an Auth.js `CredentialsProvider`), sharing the same `sessionService.ts` (and therefore the same `Session` table and revocation path) that our custom Adapter uses for Google. Auth.js is used only for the Google OAuth handshake, where database sessions work as designed.

## 3. Email verification token mechanism

- **Decision**: Single-use, randomly generated token stored hashed in a `VerificationToken` table with an expiry (24 hours), tied to one account. Requesting a resend invalidates prior unexpired tokens for that account before issuing a new one.
- **Rationale**: Mirrors the existing invitation-token pattern already established in the (previously implemented) community-invitations feature, keeping the codebase's token-handling approach consistent. Hashing the stored token (rather than storing it raw) means a database read alone can't be used to forge verification.
- **Alternatives considered**: Signed/stateless tokens (e.g., JWT with expiry claim) — rejected because revoking a specific token early (e.g., after a resend) requires the same server-side tracking anyway.

## 4. Breached/common-password check

- **Decision**: Check submitted passwords against the Have I Been Pwned Pwned Passwords API using the k-anonymity range query (only a 5-character hash prefix leaves the server; the full password and full hash never do).
- **Rationale**: Matches FR-016 exactly, is the de facto industry-standard source for this exact check, requires no license, and the k-anonymity model means no plaintext or full-hash password ever leaves CMarket's server.
- **Alternatives considered**: Bundling a static top-N common-password list (simpler, fully offline, no external dependency, but a much weaker check and stale over time). Deferred as a fallback if the external call is ever unavailable, but not the primary mechanism.

## 5. Email delivery for verification messages

- **Decision**: Send through a single internal `email` abstraction (one function: "send templated email"), backed by one transactional-email provider chosen at implementation time; nothing in this feature depends on which provider it is.
- **Rationale**: Keeps the verification-email requirement (FR-005/FR-014) decoupled from a specific vendor, consistent with Principle VII (don't couple a feature to a decision it doesn't need to make) and with the abstraction pattern already used previously in this codebase's `integrations/email` module.
- **Alternatives considered**: Hardcoding a specific provider's SDK directly into the account-creation flow (rejected: couples business logic to vendor specifics for no benefit here).

## 6. Testing framework

- **Decision**: Vitest for unit and contract-level tests (API route/server-action behavior), Playwright for the end-to-end acceptance scenarios (sign-up → verify → sign-in → sign-out, Google sign-in stub flow).
- **Rationale**: Both are first-class supported in the Next.js App Router ecosystem; Playwright can drive a real browser for the persistent-session and redirect-heavy OAuth scenarios that a pure unit test cannot exercise credibly.
- **Alternatives considered**: Jest (viable, slightly slower and more config for ESM/App Router than Vitest); Cypress (viable for e2e, Playwright chosen for better multi-browser and network-mocking support for the Google OAuth stub).

## 7. Google federated identity integration

- **Decision**: Auth.js (NextAuth) Google provider, combined with the Credentials provider for email/password, sharing one underlying `Account`/`Session` data model via the Prisma adapter.
- **Rationale**: Auth.js is the standard authentication library for Next.js App Router, supports mixing a Credentials provider and an OAuth provider against the same user record, and its Prisma adapter directly satisfies the "migrations & backups" constraint (schema owned by versioned Prisma migrations).
- **Alternatives considered**: Hand-rolled OAuth 2.0 flow against Google (rejected: reimplements what Auth.js already provides correctly, adds security risk for no gain, against Principle VII).

## 8. Untrusted-credential teardown on auto-link (security amendment, 2026-07-16)

- **Decision**: In the custom Adapter's `linkAccount`, decide "was this account unverified before this link" via the same `updateMany({ where: { id, emailVerifiedAt: null }, data: { emailVerifiedAt: now, passwordHash: null } })` call used to flip verification — its returned `count` (1 vs 0) is the atomic check-and-act signal, not a separate read-then-branch. Only when `count > 0` (the account really was unverified and this call is what verified it) does the adapter additionally delete all `Session` rows and consume all pending `VerificationToken` rows for that account (FR-018).
- **Rationale**: A separate `findUnique` read followed by an `if (wasUnverified)` branch would leave a race window between the read and the write under concurrent linking attempts. Folding the check into the `updateMany`'s `WHERE` clause makes "was unverified" and "flip to verified" a single atomic operation, exactly like the original (pre-amendment) code already did for verification alone — the security fix extends that same pattern rather than introducing a new one.
- **Alternatives considered**: Reject the Google link outright when the existing account is unverified (rejected per spec's Edge Cases: would let an attacker permanently lock the real owner out by squatting their email with an unverified account). Prompt the user to confirm before discarding the password (rejected: adds a UI flow for a case the account holder isn't even present for — the attacker's leftover password, not the real owner's).

## 9. Bind the candidate credential to the token, not the Account (security amendment #2, 2026-07-16)

- **Decision**: `signUp()` never writes to `Account.passwordHash`. The Argon2id hash of the submitted password is stored as `VerificationToken.candidatePasswordHash` on the token issued for that attempt. `consumeVerificationToken()` applies it to the account atomically, guarded by `emailVerifiedAt IS NULL` — the same `updateMany`-count pattern as decision #8 — so a token that reaches consumption after the account is already verified by any other means cannot modify `passwordHash`. Each sign-up (or resend) attempt against an unverified account issues its own token, which — via the pre-existing FR-014 invalidate-on-reissue behavior — invalidates whichever token preceded it, so only the most recently submitted attempt's credential can ever be applied.
- **Rationale**: The #8 fix only closed the Google-auto-link path; the identical root cause (a credential attached before proof of ownership) was still fully exploitable purely within the email/password flow: an attacker registers a victim's email, never verifies it; the real owner's own later sign-up attempt gets silently discarded by the pre-#9 code, but the *verification email* still goes out (correctly, to the real owner's inbox) and re-arms the *attacker's* stale credential when clicked. Moving the credential onto the token — the same object the invalidate-on-reissue mechanism already protects — reuses an existing, already-tested mechanism instead of inventing a new one, and makes "whichever attempt is verified is the one whose credential wins" a structural property rather than something each call site has to remember to enforce.
- **Consequence acknowledged, not a defect**: an account that has never been verified has no `passwordHash` at all, so it categorically cannot be signed into with a password (FR-007, revised). This is the correct behavior, not an oversight — there is no credential yet for any password to match.
- **Alternatives considered**: Requiring the verification page to have the user re-enter their password before applying it (rejected: the token itself, delivered only to the real inbox, already proves the same thing re-entry would, at the cost of extra friction and a UI flow when Constitution Principle VII favors the simpler mechanism). Keeping `passwordHash` writable at signup time but adding a separate "password confirmed at" flag checked at sign-in (rejected: two sources of truth for the same fact, more surface area for the same class of bug to recur elsewhere).

## 10. Coexisting verification tokens + sibling invalidation on success (security amendment #3, 2026-07-16)

- **Decision**: `signUp()` no longer invalidates a prior pending token when issuing a new one — `issueVerificationToken()` just inserts a new row. Only `resendVerification()` still invalidates-then-creates (renamed internally to a "reissue" path). `consumeVerificationToken()` is rewritten as a single Prisma interactive transaction (`prisma.$transaction(async (tx) => ...)`, not the array form used elsewhere in this feature): it marks the target token consumed, then attempts the guarded `account.updateMany` (still keyed on `emailVerifiedAt: null`, per decision #9); if that update's `count > 0` (this consumption is what verified the account), it additionally marks every *other* still-unconsumed token for that account consumed, in the same transaction.
- **Rationale**: Decision #9's own invalidate-on-reissue mechanism was itself the amendment #3 defect: since a competing sign-up could invalidate the legitimate holder's token, "whichever sign-up call happens last" controlled which credential could ever be applied — an attacker didn't need to guess a password or beat anyone to a click, just call sign-up last. Letting tokens coexist removes the destructive half entirely; decision #9's `emailVerifiedAt IS NULL` guard already made "first consumption wins" safe once tokens can no longer destroy each other. The interactive transaction (rather than the array form) is needed here specifically because the third statement (sibling invalidation) is conditional on the *result* of the second — array-style `$transaction` requires every query to be constructed upfront, before any intermediate result is known.
- **Consequence acknowledged, not fixed by this decision**: an attacker who consumes a token *before* the real owner does still wins that specific race. This is a phishing/timing risk inherent to any first-click-wins, email-delivered-link scheme (the same property `EMAIL_TEST_CAPTURE`-based verification, or any competing product's, would have) — not something coexisting tokens introduce or could remove without a fundamentally different verification channel. What this decision removes is the *destructive* interference between sign-up attempts, not the race itself.
- **Alternatives considered**: Requiring the client to present some prior secret (e.g., a session-scoped signup ID) to disambiguate "my" token from a stranger's, so a resend/repeat could target only the caller's own attempt (rejected: sign-up is deliberately unauthenticated and stateless between requests — introducing session-correlation here adds real complexity for a benefit the coexistence-plus-first-wins model already delivers). Locking the email address to the first `signUp()` caller until their own token expires (rejected: this is arguably worse than the current design for the real owner if the *first* caller was the attacker — it would deny the real owner a token at all for up to 24 hours).

## 11. Per-email rate limiting on sign-up/resend token issuance (security amendment #3, 2026-07-16)

- **Decision**: Count `VerificationToken` rows already created for the target `Account` within a trailing time window (`prisma.verificationToken.count({ where: { accountId, createdAt: { gte: windowStart } } })`); if at or above a fixed threshold, skip issuing a token and sending an email, but still return the endpoint's normal success response. Threshold and window are simple in-code constants (5 tokens / 15 minutes), re-used by both `signUp()`'s existing-unverified branch and `resendVerification()`, since both create `VerificationToken` rows and therefore share one naturally-computed counter — no separate rate-limit table or in-memory counter needed.
- **Rationale**: Postgres, already the source of truth for everything else in this feature, gives an exact, restart-safe, multi-instance-safe count for free from data the feature already writes — no new infrastructure (Redis, a dedicated rate-limit table, sticky in-process memory) is needed to satisfy "per email, persisted, correct across restarts/instances," which an in-memory-only counter would not be (Principle VII: don't add infrastructure a simpler option already covers). This is deliberately *per-Account* (i.e., per-email), matching FR-021's scope — it is not a global signup-spam control, which remains the pre-existing, intentionally-unspecified "standard security hygiene" the spec's Assumptions still defer elsewhere.
- **Alternatives considered**: A dedicated `RateLimitBucket` table or an in-memory `Map<email, {count, windowStart}>` (rejected: both add state to track and reset correctly for no benefit over counting rows the feature already persists). IP-based limiting (rejected: doesn't match FR-021's explicit "per-email" framing, and is trivially bypassed while also risking false positives against shared/NAT'd IPs).

## 12. Null-candidate lockout guard (security amendment #3, 2026-07-16)

- **Decision**: Fold the guard directly into `consumeVerificationToken`'s existing atomic `account.updateMany` `WHERE` clause: when `token.candidatePasswordHash` is `null`, additionally require `passwordHash: { not: null }` in that same `WHERE`. If the update's `count` comes back `0`, distinguish "already verified" (fine, existing decision #9 behavior, still returns success) from "blocked by this guard" (an extra read of the account's *current* `emailVerifiedAt` after the failed update) and return a distinct `no_credential` failure only in the latter case.
- **Rationale**: This is reachable today only via direct test/DB manipulation (no code path in this feature issues a null-candidate token except `resendVerification`'s carry-forward when an account has no token history at all — itself only reachable if an `Account` was created outside `signUp()`), but a later, separate community-bootstrap spec is expected to create `Account` rows directly, making it reachable for real; fixing the general mechanism now rather than only within `signUp()`'s own code path means it can't be silently reintroduced by a future caller of `consumeVerificationToken` that doesn't know about this specific risk.
- **Alternatives considered**: Reject issuing a null-candidate token in the first place, at `issueVerificationToken`'s call sites (rejected: `resendVerification`'s carry-forward legitimately needs to be able to return `null` for an account with no prior token history without that being a hard error at issuance time — the actual harm only occurs at consumption, so that's the more precise place to guard).
